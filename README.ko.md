# Excudo

[English](README.md) | 한국어

**전기는 공짜가 아니니까, AI도 전기값은 해야지.**

Excudo(엑스쿠도, 패키지 `excudo`)는 개인화된 AI 환경을 지속적으로 관리하고 발전시키는 엔진입니다. 이름은
라틴어로 '두드려 모양을 잡다'라는 뜻입니다. Claude Code와 Codex가 함께 따르는 규칙과 검사, 공통 스킬을
갖추고, 에이전트가 한 일을 그 기준에 맞게 다듬습니다. 이 엔진으로 운영하는 폴더를 **개인 프로젝트**라고
부릅니다. 개인 프로젝트는 자료, 판단 기준, 스킬, 자동화를 갖추고 업무, 학습, 창작의 결과를 만들어 가는
공간입니다.

**5분 안에 시작하기**

메모를 만들고 엔진을 설치한 뒤 다음 단계를 확인하세요.

```sh
npx -y excudo@^0.7.0 init my-memo
cd my-memo
npm install
npx --no-install excudo start
```

코딩 에이전트에서 이 폴더를 열고 "책 한 장 읽기를 메모에 추가해 줘"라고 요청하세요.
로컬 웹 사이트를 만들면 브라우저에서 메모를 볼 수 있습니다.

```sh
npm install --save-dev cudoc-export@^1.1.0
npx --no-install excudo site --open
```

터미널과 Markdown 편집기는 원하는 것을 쓰세요. Orca, Tine, 사이트 호스팅은 선택 사항입니다.
로컬 사이트는 호스팅 계정 없이 열립니다.
[업데이트](#엔진-업데이트), [문제 제보](#문제-제보),
[버그 양식](https://github.com/cudoment/excudo/issues/new?template=bug.yml)과
[사용성 양식](https://github.com/cudoment/excudo/issues/new?template=usability.yml)을 참고하세요.

## 시작하기

`excudo start`는 이 컴퓨터에서 마친 단계와 다음 단계를 보여 줍니다.
실행할 명령과 에이전트에게 할 말도 알려 줍니다. 엔진이 아래 목록을 관리합니다.

<!-- excudo:start (written by npm run start-docs from src/start.mjs) -->
**처음에 할 일**(차례대로):

1. **Node.js 22.16 이상**: 현재 LTS(24)를 설치합니다; https://nodejs.org
2. **작업 폴더**: 설정, 에이전트 스킬, 그래프가 든 메모 폴더를 만듭니다; `npx -y excudo init my-memo`; 또는 에이전트에게 “메모를 새로 만들어 줘”
3. **작업 폴더의 엔진**: 새 폴더에 엔진을 설치합니다; `npm install`
4. **git 저장소**: 메모의 이력입니다. save가 여기에 커밋합니다; `git init`
5. **에이전트 스킬**: init이 설치합니다. 작업 폴더에서 에이전트를 다시 엽니다; `npx --no-install excudo skills`

**필요할 때 할 일**:

1. **작업자와 독립 검토자 정하기**: 도구, 모델과 추론 수준을 직접 고르기; `npx --no-install excudo agents`; 또는 에이전트에게 “작업자와 검토자 정해 줘”
2. **Tine**: 그래프 폴더(notes/)를 Tine으로 열어 메모를 읽고 씁니다; https://tine.page
3. **휴대폰**: 그래프 폴더를 Syncthing으로 동기화하고 휴대폰의 Tine으로 엽니다; 또는 에이전트에게 “휴대폰에서도 보고 싶어”; https://syncthing.net
4. **내 홈**: 첫 화면을 직접 씁니다. 전체 트리는 아카이브로 옮겨 갑니다; `npx --no-install excudo home --own`; 또는 에이전트에게 “홈 구성 바꿔 줘”
5. **외부 업무**: 로그인한 브라우저로 이슈 트래커나 팀 게시판의 일을 가져옵니다; `npx --no-install excudo sources`; 또는 에이전트에게 “외부 할 일 가져와 줘”
6. **웹 사이트로 보는 메모**: 내 로그인으로만 열리는 Vercel에 올려 컴퓨터와 휴대폰에서 봅니다; `npx --no-install excudo site setup`; 또는 에이전트에게 “사이트 설정해 줘”
7. **웹 사이트에서 바꾸는 할 일 상태**: 웹 사이트에서 할 일 상태를 바꾸면 이 컴퓨터가 메모에 반영합니다; `site: { inbox: true }`; `npx --no-install excudo site setup`; 또는 에이전트에게 “사이트에서 할 일 상태를 바꾸게 해 줘”

`npx -y excudo start`(작업 폴더에서는 `npx --no-install excudo start`)로 진행 상태를 확인합니다. `excudo start --report`는 모든 단계와 이어서 할 곳을 보여 줍니다.

## 메모가 하는 일

개인 프로젝트의 중심은 메모입니다. 메모는 Markdown 노드를 담은 폴더이며, [Tine](https://tine.page)에서
컴퓨터와 휴대폰 모두 무한 트리로 보입니다. 맨 위 목록과 결정은 사용자가 맡고, 정리는 에이전트가 맡습니다.
엔진은 어느 개인 프로젝트에서나 쓸 수 있는 명령, 검사, 스킬을 맡고, 자료와 설정과 인증 정보는 각 개인
프로젝트에 둡니다.

개인 프로젝트의 이름은 'Excudo + 용도'로 짓기를 권장합니다. 업무 자동화용은 **Excudo Works**, 스터디용은
**Excudo Lab**처럼 짓습니다. 엔진은 'Excudo' 또는 '엔진'으로만 부르고, 개인 프로젝트는 이름 전체나 '이
프로젝트'로 부릅니다. 개인 프로젝트의 에이전트도 '엔진'을 이렇게 해석하고, 메모가 아닌 것을 고치기 전에는
엔진과 이 프로젝트 가운데 어느 쪽을 고칠지 사용자에게 묻습니다.

- **[짧게 유지되는 첫 화면](#맨-위는-짧게-자세한-내용은-아래에):** 에이전트가 기록한 내용을 알맞은
  노드 아래에 두고, 바뀐 곳 위의 요약을 최신으로 맞추며, 자세한 내용은 지우지 않고 아래에 접어 둡니다.
- **[답하기 전에는 옮기지 않습니다](#정리-인터뷰):** 정리 인터뷰가 근거와 추천을 붙여 네 건 이하씩
  묻고, 답한 묶음마다 따로 커밋해서 되돌릴 수 있게 합니다. 완료는 사용자만 표시합니다.
- **[외부 작업](#외부-작업-가져오기)과 [최신 지식](#지식을-최신으로-유지하기):** 이슈, 요청, 멘션을
  로그인한 브라우저로 한 번씩만 가져오고, 지켜보는 저장소와 페이지의 변경을 지식 노드에 반영합니다.
- **[검증하는 스킬만 만듭니다](#스킬은-코드를-품습니다):** 모든 스킬은 코드를 품습니다. 적어도
  요구 사항을 확인하는 검사와, 그 검사가 통과해야 하는 경우와 실패해야 하는 경우를 담습니다.
  `skills lint`가 그 경우들을 직접 실행해 점수를 매기므로, 프롬프트만 줄여 둔 것이나 실패할 수 없는
  검사는 스킬로 인정하지 않습니다. 되풀이된 요청도 이 기준을 넘을 때만 새 스킬이 되고, 기준에서
  벗어나면 쓰지 않게 됩니다.
- **[요청에서 배웁니다](#요청에서-배우기):** 에이전트에게 입력한 요청을 읽어서(원문은 git에 넣지
  않습니다) 오래 갈 결정은 노드로, 되풀이된 일은 스킬로 자기 말로 정리합니다.

## cudoc 기반

Excudo는 [cudoc](https://www.npmjs.com/package/@cudoment/cudoc)(`@cudoment/cudoc`)에
의존하며, npm이 함께 설치합니다. cudoc은 엔진이 쓰는 별도의 의존성으로, 트리(조상, 순서, 요약)와 생성 뷰를
이루는 임베드를 제공합니다. Excudo는 그 위에 아웃라이너 형식, 검사, 정리 질문, 스킬을
더합니다. 엔진도 개인 프로젝트도 cudoc 제품군이 아닌 독립 프로젝트이므로 엔진의 문제는 이 저장소에서, cudoc
라이브러리 자체의 문제는 cudoc에서 다룹니다.
파일은 Logseq 형식을 따르며, Tine에서 검증했고 Logseq에서는 아직 검증하지 않았습니다.

## 그 밖의 기능

- [홈을 사용자의 페이지로](#홈을-사용자의-페이지로-쓰기): 홈에서 한 일을 체크하고 구성을 정하며, 전체 트리는 아카이브 뷰에 남습니다.
- [자세한 내용 찾기](#자세한-내용-찾아보기): 오래전에 지운 줄도 `find --history`로 찾습니다.
- 끝낸 일은 git 이력의 날짜로 달마다 보관합니다(`archive`).
- [노드의 작업 폴더](#노드의-작업-폴더): 경로, 브랜치, 창 이름 줄을 최신으로 맞춥니다.
- [사용자의 형식으로 쓴 파일](#사용자의-형식으로-파일-유지하기): 할 일 목록 같은 파일을 저장할 때마다 메모로 다시 씁니다.
- 블록 id, 참조, 임베드를 검사하고 고칩니다(`fix`).
- 회고, 스킬 관리, 외부 출처 갱신을 예약 실행하고, 판단이 필요한 것은 질문으로 남깁니다.
- [Tine으로 휴대폰 동기화](#tine과-휴대폰-동기화)를 하며, 모든 메시지를 영어와 한국어로 제공합니다.

## 엔진 업데이트

새 버전과 변경 이력을 확인한 뒤 설치 여부를 정하세요.

```sh
npx --no-install excudo update
npx --no-install excudo update --channel next --json
npx --no-install excudo update --apply
```

기본 채널 `latest`는 안정 버전입니다.
`--channel next`는 베타 태그와 안정 태그를 비교해 높은 버전을 고릅니다. `--channel`을 주지 않으면 설치한 버전이 프리릴리스일 때 `next`를, 아니면 `latest`를 따릅니다.
명령은 설치 버전, 레지스트리 버전, 제공되는 변경 이력과 설치 명령을 출력합니다.
작업 폴더에서 `--apply`를 붙여야 설치하고 스킬을 갱신합니다.

설치한 엔진 스킬 사본은 지문을 기록하며, 수정하지 않은 사본만 교체합니다.
사용자 수정, 추가 파일과 외부 링크는 보존합니다.
캐시 폴더의 `skill-backups` 아래에 백업하고 경로를 출력합니다.
출력한 백업 경로에서 수정본을 비교하고 합친 뒤 다시 실행하세요.

조회 실패는 네트워크, 인증, 태그 없음으로 나눠 알리고 성공으로 끝납니다.
설치 실패는 npm 오류의 마지막 부분을 출력하고 오류로 끝납니다.
`--apply` 뒤에는 `excudo start --report`와 출력한 설정 검사를 실행해 빠진 템플릿 규칙을 확인하세요.
버전별 GitHub 릴리스와 CHANGELOG 링크도 출력하며, npm 메타데이터에는 최신 절을 담습니다.

## 문제 제보

컴퓨터에서 초안을 만들고 검토한 뒤 공유하려면 GitHub 이슈 링크를 여세요.

```sh
npx --no-install excudo feedback --title "빌드 실패" --message "일어난 일과 기대한 결과"
npx --no-install excudo feedback --out feedback.md --json
```

초안은 사용자 설명을 먼저 싣고 버전, 운영체제, 시작 단계 상태와 고정된 진단 식별자만 붙입니다.
엔진이 모르는 실행 단계는 `custom-step`, 실패한 스킬 검사는 `skill-check`로 표시합니다.
자유 문장으로 쓴 실행 상세와 스킬 이름은 `--details`를 붙여야 넣습니다. 보내기 전에 검토하라는 안내도 붙입니다.

홈, 작업 폴더, 그래프와 실제 경로를 지웁니다.
Windows 드라이브 경로, 두 단계 이상인 절대 경로, 이메일, IP 주소와 비공개 호스트도 지웁니다. `--details`에서는 그 밖의 경로도 줄 끝까지 지웁니다.
URL은 `github.com`과 `npmjs.com`만 남깁니다.

추가로 가릴 문자열은 `excudo.config.mjs`에 `private: ["비밀 값"]`으로 적으세요.
`private: true`를 붙인 객체 안의 문자열도 지웁니다.
설정이 깨져도 `feedback`과 `start --report`는 실행하며, 기본 출력은 비공개 오류 원문을 생략합니다.

명령은 제보를 전송하거나 브라우저를 열지 않습니다. `--out`은 가린 초안만 저장합니다.

## 스킬로 시작하기

Node.js 22.16 이상(현재 LTS인 24 권장)과 Agent Skills를 읽는 에이전트가 필요합니다. 저장소 공개 뒤에는 다음으로
입구 스킬을 받습니다.

```sh
npx skills add cudoment/excudo --skill excudo-setup
# 열 스킬을 모두 받으려면 다음을 씁니다.
npx skills add cudoment/excudo
```

에이전트에게 "메모를 새로 만들어 줘"라고 말합니다. 입구 스킬이 위치와 언어를 묻고 npm
엔진으로 `init`을 한 뒤 작업 폴더에서 `npm install`을 합니다. `init`이 열 스킬을
`.agents/skills/`에 복사하고 `.claude/skills/`에서 연결합니다. 그 폴더에서 에이전트를 다시
열면 됩니다.

저장소 맨 위의 `skills/`가 배포 원본이며 입구만 받으려면 `--skill`을 씁니다.
원격과 레지스트리 설치 경로는 첫 게시 뒤에 실제로 확인합니다.

| 작업 | Claude Code | Codex |
| --- | --- | --- |
| 기록 | `/excudo-capture 여권 갱신을 메모해 줘` | `$excudo-capture 여권 갱신을 메모해 줘` |
| 정리 인터뷰 | `/excudo-distill` | `$excudo-distill` |
| 설치와 설정 | `/excudo-setup` | `$excudo-setup` |
| 외부 출처 | `/excudo-sources 외부 할 일 가져와 줘` | `$excudo-sources 외부 할 일 가져와 줘` |
| 지식으로 답하기 | `/excudo-recall 사이트에서 바뀐 게 뭐야?` | `$excudo-recall 사이트에서 바뀐 게 뭐야?` |
| 회고 | `/excudo-reflect` | `$excudo-reflect` |
| 스킬 만들기 | `/excudo-skills` | `$excudo-skills` |
| 할 일 파일 유지 | `/excudo-export` | `$excudo-export` |
| 다른 앱의 메모 따라가기 | `/excudo-follow` | `$excudo-follow` |
| 에이전트에게 맡긴 일 처리 | `/excudo-queue` | `$excudo-queue` |

한국어나 영어로 그냥 요청해도 됩니다. 스킬마다 Markdown 지침과 스크립트가 함께 있으며, 적어도
스킬의 작업이 요구 사항을 충족했는지 확인하는 검사가 들어 있습니다("스킬은 코드를 품습니다" 참고).
생성, 검사, 이동, 보관, 커밋은 엔진이 하고, 넣을 자리와 요약과 결정은 스킬이 다룹니다. 네트워크는 설치
단계에서만 필요하며, 그 뒤에는 `npx --no-install excudo`로 로컬 엔진만 부릅니다.
없으면 작업 폴더에서 `npm install`을 먼저 합니다. 오래된 스킬은 `skills --force`로 갱신합니다. 패키지와 내용이 다른 사본은 한 번만 백업하고 그대로 두며, `skills --replace <이름>`이나 `--replace-all`이 백업한 뒤 교체합니다.
`skills --global`은 `~/.agents/skills/`에 설치하고, 학습한 스킬처럼 홈 폴더에 폴더가 있는 에이전트마다
`~/.claude/skills/`와 `~/.codex/skills/`에 연결합니다. 다른 폴더에서
전역 스킬을 부를 때는 `EXCUDO_ROOT`를 지정합니다. 엔진의 로컬 복제본을 `file:`로 설치한 작업
폴더는 스킬을 복사하지 않고 복제본에 연결할 수 있습니다. `skills --link --force`로 연결하면 스킬이
복제본과 함께 바뀌며, `skills --copy`는 다시 복사합니다.

### 명령줄로 시작하기

npm 게시 뒤에는 다음을 씁니다.

```sh
npx -y excudo@^0.5.0 init my-memo --locale ko
cd my-memo
npm install
git init
npx --no-install excudo check
```

게시 전에는 로컬 복제본에서 다음을 실행합니다.

```sh
npm install
node bin/excudo.mjs init ../my-memo --locale ko
```

새 작업 폴더로 들어가 `npm install`을 합니다. 의존성은 복제본을 가리킵니다.
`EXCUDO_PACKAGE`에 로컬 폴더나 tarball을 지정하면 입구 스킬에서도 같은 흐름을
시험할 수 있습니다. `init --example`은 [영문 더미 예시](example/notes)를 만들며 다른 언어를
지정하면 거부합니다.
`--graph`는 그래프 폴더 이름을 바꿉니다.

## 맨 위는 짧게, 자세한 내용은 아래에

홈에는 맨 위 노드마다 이름, 하위 전체의 열린 할 일 수, 요약이 한 줄로 보입니다. 기록할 때도
정리할 때도 이 목록을 짧게 유지합니다. 자세한 내용은 지우지 않고 아래에 깊이 접어 두었다가
필요할 때 펼치거나 검색해서 찾습니다. 각 노드 끝에는 홈부터 그 노드까지의 위치와 그 아래
트리 전체가 붙습니다. 요약은
노드 한 곳에만 쓰며, cudoc API가 계층과 순서와 값을 만들고 이 엔진은 아웃라인으로 씁니다.

기본 홈은 처음 쓰는 하나의 예입니다. 홈을 넘겨받으면('홈을 사용자의 페이지로 쓰기') 원하는 대로 바꿉니다.

기본 홈은 두 영역으로 나뉩니다. 위쪽 "생각과 계획"에는 트리와, 접어 둔 방침, 생각 쿼리가 있어 영역마다 지금의
방향과 정한 것을 봅니다. 아래쪽 "업무와 자동화"는 "진행 중", "맡긴 일"(큐 태그를 붙인 열린 할 일),
"검토 대기"(에이전트가 남긴 `WAITING 검토:` 줄)를 펼치고 대기와 확인할 것은 접어 둡니다. 나누는 기준은
주제가 아니라 생각과 실행입니다. 한 영역의 방향은 위에, 다음 할 일은 아래에 보이고, 둘 다 자기 노드에
있으며 홈은 이를 베끼지 않고 트리와 쿼리로 보여 줍니다. 각 절은 접힌 제목 아래에
쿼리를 둔 블록이 아니라 제목과 접힘을 스스로 가진 쿼리 하나입니다
(`{{query (task WAITING) {:title "대기" :collapsed? true}}}`). 휴대폰의 Tine은 접힌 블록의 화살표를 줄
오른쪽 끝에 흐리게 그리고 문서 모드에서는 숨겨서 접힌 제목이 일반 텍스트처럼 보이지만, 쿼리의 제목과
결과 수, 화살표는 어느 기기에서나 보입니다. 쿼리를 펼친 상태는 그 기기에만 남고 파일을 다시 쓰지
않습니다. Tine은 괄호 식 쿼리 뒤의 옵션만 읽으므로 페이지 참조나 글자 검색은 `(and …)`로 감쌉니다.
`tine export static`(0.7.1)은 이 옵션을 읽지 못해 그런 쿼리를 글자 그대로 보여 줍니다. 예전 템플릿으로
만든 홈은 같은 방식으로 바꾸기 전까지 접힌 제목을 그대로 둡니다. `check`와
`save`는 첫 목록의 폭, 요약 초과, 뒤처진 요약, DOING 수를 보여 줍니다. 완료와 기록은 메타
노드이므로 첫 목록의 폭에서 뺍니다. `top.visibleLines`는 현재 접힘을 반영한 홈의 빈 줄을
제외한 표시 원문 행 수입니다. 쿼리 결과와 화면 너비에 따른 줄바꿈은 제외하고 DOING 수는
별도로 봅니다. 첫 화면이 읽기 쉬워지고 접어 둔 내용을 다시 찾을 수 있는지로 정리를 평가합니다.

## 정리 인터뷰

메모는 쌓입니다. `excudo-distill`은 맨 위 목록부터 군더더기를 찾고 근거와 추천을 붙여
네 건 이하씩 묻습니다. 같은 노드나 개별 항목의 여러 사유는 한 질문으로 묶습니다. 답을 받기
전에 내리거나 지우지 않습니다. 나중에 찾아볼 내용은 관련 노드 아래나 완료 보관으로 내리고,
다시 볼 일이 없는 것만 지웁니다. 열린 할 일이 없다고 참고 자료가 쓸모없거나 끝난 것은
아니며 사용자가 가치를 판단합니다. 남김의 결정은 질문 전체에 적용합니다.

> 에이전트: `projects/참고.md:5`는 열린 할 일이 없는 참고 방법입니다. 현재 작업 아래로
> 작업에 쓰인다면 내리거나 맨 위에 남길 수 있습니다. `projects/옛 계획.md:6`의 초안 요청은
> 기한이 지났습니다. 기한 변경(추천), 완료 여부 확인 후 보관, 지움 중 무엇으로 할까요?
>
> 사용자: 1 내림, 2는 11월 3일까지로 바꿔 줘.

그 묶음을 반영하고 맨 위까지 요약을 확인한 뒤 별도 커밋으로 저장합니다. 내린 것은 펼치거나
검색하면 찾을 수 있고, 지운 것도 git 이력과 `find --history`로 찾을 수 있습니다. 엔진은 후보를
찾고 스킬은 물어서 사용자의 결정을 반영합니다. 각 묶음은 그래프와 `review.json`을 함께
저장하므로 `git revert <묶음-커밋>`으로 해당 답변과 내용만 되돌릴 수 있습니다. 초기 스냅샷과
이전에 저장한 묶음은 유지됩니다.

다른 앱에서 옮긴 정리되지 않은 메모(`ㄴ` 들여쓰기, 제목 없는 줄, 주소가 섞인 목록)를 붙여 넣고
정리해 달라고 하면, 스킬은 바로 옮기지 않습니다. 먼저 스크립트(`scripts/raw.mjs`)가 줄마다 지금
메모와 맞춰 봅니다. 이미 있는 할 일이나 생각, 끝났거나 보관된 줄, 비슷하기만 한 줄, 새 줄로
나눕니다. 그다음 지금 관심을 두는 영역, 생활에서 할 일, 보관할 것, 새 줄을 둘 곳을 네 건 이하씩
묻고, 답을 받은 줄만 반영합니다. 검사(`--raw`)는 새 줄과 비슷한 줄을 모두 물었는지, 답하지 않은 줄이
메모에 더해지거나 옮겨지지 않았는지 확인합니다.

## 노드와 생성물의 경계

```markdown
# 글 이전
옛 글을 옮기면서 링크를 유지합니다.

- DOING 글 내보내기
- TODO 옛 주소 대응표 만들기
- 생각: 이전 과정에 관해 글 쓰기
```

파일 하나가 노드 하나입니다. 첫 줄은 파일 이름과 같은 제목이고 다음 문단은 지금의 핵심
요약입니다. 이름은 그래프 전체에서 겹치면 안 됩니다. `X.md`의 하위 노드는 `X/`에 둡니다.
`projects/` 같은 맨 위 분류 폴더는 층을 만들지 않습니다. 링크는 `[[페이지]]`로, 할 일은
`TODO`, `DOING`, `WAITING`, `DONE`으로 씁니다. Tine에서 GFM의 `- [ ]`는 글자로 보입니다.
목록 뒤에는 제목만 둡니다. 뒤의 들여 쓰지 않은 문단과 표는 Tine에서 체크할 때 마지막
항목의 본문으로 흡수됩니다. 제목의 내용은 바로 다음 줄에서 시작하고, 제목 위에는 빈 줄 하나를
둡니다. 제목 아래 글은 다음 목록 항목이나 제목 전까지 제목 블록에 속하고, Tine은 그 블록 안의
빈 줄을 빈 공간으로 보여 줍니다. 그래서 제목 아래에는 문단 하나(맨 위 제목 아래에서는 요약)만
두고 나머지 글은 목록 항목으로 씁니다. 생성물도 이 형식을 따르며, 빈 줄이나 문단을 목록 항목으로
바꾼 것 같은 형식 변경은 본문 변경으로 세지 않습니다. Tine은 목록 밖의 제목을 주변 항목과 같은 깊이로
보여 줍니다. 그래서 직접 구성하는 페이지(홈 등)에서 항목을 제목 아래로 묶어 보이려면 제목 블록
`- ### 업무`를 두고 그 항목을 아래에 들여 씁니다. 아래에 들여 쓴 항목이 없는 목록 항목 제목은
아웃라이너가 고친 흔적으로 봅니다(`bullet-heading`).

홈의 원본은 `views/홈.mdx`입니다. 표준 cudoc 임베드라 나중에 SSG에서도 같은 트리를 쓸 수
있습니다.

````markdown
```cudoc-embed
sources: [/]
render:
  type: tree
  open: 0
  columns: [link, { value: { extractor: openTasks } }, summary]
  order: [..., 완료, 기록]
```
````

`outline` 펜스의 쿼리는 그대로 복사하고, `nodes` 펜스는 트리의 일부를 이름으로 골라 보여 줍니다("홈을 사용자의 페이지로 쓰기"). Tine은 `.mdx`를 읽지 않습니다. 생성된 `홈.md`의
첫 줄은 `생성:: views/홈.mdx`이며 각 노드의 생성물은 `## 하위 문서`부터입니다. 생성물은 위치 줄
(`위치: [[홈]] › [[상위 노드]] › 노드`)로 시작하고, 하위 노드가 있으면 그 트리가 이어집니다.
직접 고치지 않습니다. 제목과 할 일은 Markdown 구조로 구분하므로 펜스, 들여쓰기 코드, HTML, 인용문
예시는 보존합니다. 빌드는 직접 쓴 본문을 그대로 두고 손으로 고친 생성물을 보호하며 종료
코드 2를 냅니다. `collapsed::`의 펼침과 접힘도 유지합니다. `init`도 해당 뷰의 생성물이 아닌
기존 홈을 덮어쓰지 않습니다. macOS Syncthing의 NFD 파일 이름도 NFC로 비교하며 다시 쓸
때 디스크의 이름 형태를 유지합니다. 캐시는 그래프 밖의 `.excudo/`에 둡니다.
보호 기록은 하위 전체를 옮길 때 함께 옮기고, 묶음 되돌리기를 위해 이전 생성물의 기록도
유지합니다. 캐시 삭제로 기록이 없으면 기존 생성물과 현재 생성 결과가 같은 경우에만 다시
보호 기록을 만듭니다. 다르면 빌드를 차단하므로 내용을 보존한 뒤 `build --force`로 명시적으로
덮어씁니다. 휴대폰에서 노드를 고치면 Tine이 `## 하위 문서` 제목을 목록 항목(`- ## 하위 문서`)으로
저장하고 그 위에 빈 항목을 남길 수 있습니다. 그 절에 다른 글이 없으면 빌드가 제목을 되돌리고 빈
항목을 지웁니다. 다른 글이 있으면 멈추고 그 글을 절 위로 옮기라고 알립니다. cudoc이 수집한 문서는
남기지 않습니다. 명령마다 임시 폴더에 수집한 뒤 지우므로 미리 보기는 아무 파일도 쓰지 않습니다.

## 자세한 내용 찾아보기

PC와 휴대폰의 Tine에서는 홈의 맨 위 노드를 펼쳐 내려가거나, 노드 끝의 하위 트리를 따라
내려가거나, 검색합니다. Tine은 페이지를 파일 이름으로만 나열하므로, 노드 끝의 위치 줄로 그
노드가 어디에 있는지 확인하고 위로 이동합니다. `init`은 홈을 사이드바 즐겨찾기
(`logseq/config.edn`의 `:favorites`)에 고정합니다. 끝낸 일은 완료 → 완료 2026 → 완료 2026-10 아래에 접혀 있습니다.
완료에는 최근 `doneKeep`건만 남고 넘친 것은 달별 노드에 남습니다. 달은 완료에 들어온 날의
git blame으로 정하며 알 수 없으면 보관하는 날을 씁니다. 이력을 읽지 못하면 보관을 멈춥니다. 끝난 노드 전체도 보관할 수 있습니다.
`archive --canceled`는 CANCELED로 표시한 항목만 옮깁니다. 예약 실행이 하지 않기로 한 일을 치우고, 끝낸 일은 다음 정리 때까지
그 자리에 둘 수 있습니다.

에이전트의 조회는 `tree`로 위치를 짐작하고, 본문을 읽고, `find`로 찾고, 그래도 없으면
`find --history`로 지운 줄까지 찾습니다. 조회에는 답만 하고 메모는 고치지 않습니다.

## 홈을 사용자의 페이지로 쓰기

첫 화면을 직접 고르고 싶으면 홈을 한 번 넘겨받습니다.

```sh
npx --no-install excudo home --own
```

`views/홈.mdx`는 전체 트리를 담는 `views/아카이브.mdx`가 되고, `홈.md`는 사용자의 페이지가
됩니다. 새 홈에는 트리 맨 위에 있던 노드의 링크와 아카이브 링크가 들어가고, "지금"처럼 뷰에
있던 다른 절("업무와 자동화" 등)도 접힘 상태와 함께 옮겨집니다. 트리의 노드는 옮기거나 지우지 않습니다. 생성된
홈을 손으로 고쳤거나, 홈 뷰를 링크하거나 임베드하는 페이지가 있거나, 그래프에 참조 오류가 있으면
아무것도 바꾸지 않고 멈추며, 쓰는 도중 실패하면 모든 파일을 되돌립니다. 이후로
엔진은 홈을 쓰지 않습니다. 사용자는 홈에서 한 일을 체크하고 홈의 구성을 정합니다. 에이전트는 스스로나
예약 실행으로 홈을 고치지 않고 넣을 링크를 제안하며, 사용자가 절을 더하거나 쿼리를 좁히거나 링크를
넣어 달라고 요청하면 그 요청을 기준으로 홈을 정비하고 나머지는 그대로 둡니다. 아카이브 페이지는 예전 홈처럼
생성되며 모든 위치 줄은 아카이브에서 시작합니다. 홈에서는 어느 깊이의 노드든 링크할 수 있고
링크를 원하는 대로 묶어도 됩니다. 링크한 노드의 끝에는 여전히 그 노드의 하위 트리가 있습니다.

홈을 직접 쓸 때는 원하는 대로 구성합니다. 기본 홈의 두 영역(위에 생각, 아래에 업무)은 하나의 예입니다.

어떻게 구성하든 홈에는 아무것도 베끼지 않습니다. 업무는
쿼리로 보여 줍니다. 진행 중인 일, 다음 할 일, 출처의 항목(노드 페이지나 주소로), 에이전트에게 맡긴 일,
`WAITING 검토:` 줄, 그 밖의 대기가 여기에 해당합니다. 생각의 영역은 홈이 임베드하는 생성 뷰로 보여 줍니다.
뷰의 `nodes` 펜스는 트리의 일부를 노드 이름으로 골라, 트리처럼 줄마다 열린 할 일 수와 요약을 보여 주고
하위는 접어 둡니다.

````markdown
```nodes
depth: 2
except: [보관]
```
````

`depth`는 보여 줄 단계 수(없으면 2)이고, `except`는 그 노드를 하위와 함께 빼며, `from: <노드>`는 맨 위
대신 그 노드 아래부터 보여 줍니다. 완료와 기록은 늘 뺍니다. 이름은 노드가 어디로 옮겨도 그 노드를
따라갑니다. `from`이 노드가 아닌 이름이거나 펜스가 모르는 설정이 있으면 빌드가 멈춥니다. 펜스를 `views/생각과 계획.mdx` 같은 뷰에 쓰고 홈에
`{{embed [[생각과 계획]]}}`을 두면, 빌드가 그 페이지를 최신으로 유지하고 홈에는 임베드 줄만 남으므로
사용자가 쓰는 부분과 엔진이 쓰는 부분이 섞이지 않습니다. 홈이 임베드한 뷰가 보여 주는 노드와 홈이
임베드한 노드 페이지는 홈에서 닿는 것으로 셉니다. 뷰를 링크만 한 것은 세지 않습니다. 그렇지 않으면
아카이브 링크 하나로 모든 노드가 닿게 됩니다. `check`는 홈에 노드의 할 일을 그대로 적으면 경고합니다
(`home-copy`). 쿼리로 보여 주면 됩니다.

`home`은 홈이 가리키는 노드, 홈이 임베드한 페이지와 그 뷰가 홈에 보여 주는 노드 수, 페이지가 없는 링크,
홈에서 직접도 하위로도 닿지 않는 맨 위 노드를 알려 줍니다. `review`는 홈의 폭이나 맨 위 요약을 판단하지 않고, 그런 맨 위 노드를 어디에 둘지
묻습니다(`home-outside`). 뒤처진 요약은 홈이 가리키는 노드부터 묻습니다. `check`는 홈에 노드
규칙을 적용하지 않고 줄 형식 문제는 경고로만 알리며, `top`의 첫 목록은 홈의 첫 목록으로 셉니다.
`remove`는 홈이 가리키는 노드와 그 위의 노드를 `--force` 없이는 지우지 않습니다.

Tine에서 새 링크를 따라가 만든 페이지는 Tine의 기본 페이지 폴더인 `pages/`에 생깁니다. 이
페이지는 트리에 놓일 때까지 트리와 노드 규칙에서 빠집니다. `inbox`가 목록으로 보여 주고
`move <페이지> <부모>`로 트리에 놓으며, 놓은 뒤에는 다른 노드처럼 제목과 요약이 필요합니다.

## 외부 작업 가져오기

이슈 관리 도구, 팀 게시판, 요청이나 멘션을 메모로 가져올 수 있습니다. 엔진은 네트워크에 직접
접속하지 않습니다. 에이전트가 사용자가 로그인한 브라우저(브라우저 자동화 도구나 앱 내장 브라우저)로
출처를 열어 항목을 모으면, 엔진이 항목을 둘 곳을 정하고 메모에 이미 있었던 항목을 거르며 기록을
남깁니다. 출처는 `excudo.config.mjs`에 적습니다.

```js
sources: [
  {
    name: "jira",                                // 명령에서 쓰는 이름
    label: "Jira",                               // 항목에 키가 없을 때 쓰는 링크 글자
    url: "https://jira.example.com/issues/?jql=assignee%3DcurrentUser()",
    collect: "나에게 배정된 미해결 이슈",          // 에이전트가 모을 것
    key: "[A-Z][A-Z0-9]+-\\d+",                  // 이 키를 적어 둔 노드로 항목을 보냅니다.
    node: "업무",                                // 그런 노드가 없으면 여기에, 이것도 없으면 오늘 저널에 둡니다.
    complete: true,                              // 이 페이지가 열린 항목을 모두 보여 줍니다.
    finished: "ask",                             // "settle"이면 걸린 항목이 모두 끝난 할 일을 DONE으로 바꿉니다.
    script: async ({ since, url }) => { /* 페이지에서 실행되어 항목을 JSON으로 돌려줍니다. */ },
    actions: { create: { script: async (fields) => { /* … */ }, notes: "채울 내용" } },
  },
],
```

에이전트에게 이슈를 메모로 가져와 달라고 요청하면 `excudo-sources` 스킬은 먼저 필요한 출처에
모두 로그인되어 있는지 확인합니다. 로그인이 풀린 출처가 있으면 작업 전에 알리고, 사용자가 로그인한
뒤에 이어서 진행합니다. 그다음 출처 페이지에서 스크립트를 실행하거나(`sources script <이름>`) 페이지를
읽습니다. 그다음
`ingest <이름> <파일> --dry-run`으로 미리 보여 주고, 사용자가 확인하면 새로 열린 항목을
`- TODO <제목> [<키>](<주소>)` 형태로 한 번씩 넣습니다. 새 줄은 그 노드의 첫 소제목 앞 본문에
들어가며, 지식 노드에만 적힌 키로는 항목을 그 노드에 보내지 않습니다. 항목은 `{ id, title, url }`이며 `done`,
`state`, `marker`(평범한 줄은 `""`), `node`(둘 노드), `skip`(다시는 넣지 않음), `covers`(이슈 설명에
링크된 요청처럼 그 항목의 일이 대신하는 다른 페이지)를 더할 수 있습니다.
그래프 어디엔가 링크가 있거나 전에 넣은 적이 있는 항목은 줄을 지우거나 보관한 뒤에도 다시 넣지
않으며, 끝난 항목도 넣지 않습니다. 출처마다 가져온 내용은 `review.json` 옆의 `sources.json`에
남고, `snapshot`과 `save`가 그래프와 함께 커밋합니다. 출처가 180일 동안 보여 주지 않은 항목은 그
항목을 가리키는 열린 할 일이 없으면 기록을 줄입니다. 메모에 들어온 적이 없는 항목은 지우고, 들어온
적이 있는 항목은 id와 링크만 남겨서 다시 넣지 않습니다.

완료는 사용자가 정합니다. 출처에서는 끝났는데 메모에서 열려 있는 항목, 열린 항목을 모두 보여 주는
출처의 목록에서 빠진 항목은 `review`에서 `source-closed`, `source-gone` 질문이 됩니다. 사용자가 출처에서
직접 완료를 표시한다면 그 출처에 `finished: "settle"`을 정합니다. 그러면 `ingest`가 실행될 때마다, 할 일
자신의 글에 링크된 항목이 모두 정리하는 출처에서 끝났을 때 그 할 일을 `DONE`으로 바꾸고 `settled`로
알립니다. 페이지의 일부를 가리키는 링크(`…#comment-3`)는 그 일부를 뜻하고, 항목의 `covers`도 그 항목의
링크로 셉니다. 아직 열린 항목이나 묻기로 한 출처의 항목이 있으면 할 일을 그대로 둡니다. 출처의 항목처럼
보이지만 어느 출처도 수집하지 않은 링크(다른 사람이 맡은 일, 출처를 처음 수집하기 전의 이슈)가 있어도 그대로
둡니다. 출처의 항목과 호스트와 경로가 같거나(숫자 부분은 보지 않음) 그 출처의 호스트에서 출처의 `key`가 보이는
링크가 그런 링크입니다. 기다리는(WAITING) 할 일과 아래에 열린 할 일이 있는 할 일도 그대로 두며, 안내 페이지 같은
다른 링크는 판정에 쓰지 않습니다. 평범한 줄을 넣는 출처(`marker`가 빈 문자열인 멘션 등)의 항목도 판정에 쓰지
않습니다. 다만 그런 출처가 본 링크라도 그 일이 끝났는지는 알 수 없으므로, 출처의 항목처럼 보이는 링크는 그대로 할
일을 열어 둡니다. 사용자가 건너뛰기로 한 항목(`skip`)의 링크만 판정에서 뺍니다. 출처 스킬과 정리 스킬의
검사가 에이전트에게 이 규칙을 지키게 합니다. 작업을 시작한 커밋(`--since`)과 비교해, 엔진이 정리하지 않았고
사용자가 끝났다고 하지도 않은(`--allow-done <할 일 글>`) 할 일이 닫혔으면 실패합니다. 에이전트는
사용자가 요청하고 내용을 확인한 경우에만 출처의 `actions`나 사이트의 입력 화면으로 출처에 항목을
만들거나 바꿉니다. 스크립트는 페이지 안에서 그 페이지의 로그인 세션으로 실행되는 독립된 함수나 그
원문이며, 인증 정보를 넣지 않습니다. 로그인하지 않은 페이지에서는 빈 목록 대신 오류를 내게 합니다.
열린 항목을 모두 보여 주는 출처가 빈 목록을 돌려주면 모든 항목이 목록에서 빠진 것으로 읽힙니다.

이 스킬은 미리 모은 항목으로 예약 실행(cron 같은 타이머가 에이전트의 비대화형 모드를 부르는 방식)할
수도 있습니다. 답할 사람이 없으므로 예약 실행 자체를 항목을 가져오라는 사용자의 요청으로 봅니다. 같은
일을 적은 열린 할 일이 이미 있으면 새 줄 대신 그 줄 끝에 항목의 키를 붙이고, 나머지 항목은 엔진이
정한 자리에 둡니다. 끝났거나 목록에서 빠진 항목은 질문으로 남기고, 로그인이 필요한 출처는
건너뜁니다.

## 지식을 최신으로 유지하기

메모에는 프로젝트와 지켜보는 페이지에 관해 아는 것도 담을 수 있고, 에이전트가 그것을 최신으로
유지합니다. 저장소, 폴더, 웹 페이지마다 지식 노드를 정합니다.

```js
sources: [
  { name: "site", kind: "repo", path: "~/work/site", node: "사이트 저장소", aliases: ["~/old/site"] },
  { name: "notices", kind: "page", url: "https://forum.example.com/c/notices", node: "공지",
    script: async () => (await (await fetch("/c/notices.json")).json()).topics.map((t) => ({ id: t.id, title: t.title })) },
  { name: "docs", kind: "repo", path: "~/work/docs", node: "문서 저장소", watch: "commits" },
  { name: "archive", kind: "repo", path: "~/old/prototype", node: "지난 프로젝트", enabled: false },
],
knowledge: ["지식"], // 주제처럼 참고 지식만 담는 노드입니다.
```

`changes`는 저장소를 직접 읽어서(커밋과 커밋하지 않은 변경, 폴더라면 의존성과 빌드 결과를 뺀
파일 목록) 노드를 마지막으로 갱신한 뒤 바뀐 출처를 알립니다. 늘 작업 중인 변경이 있는 저장소는
`watch: "commits"`로 커밋만 지켜볼 수 있습니다. 커밋하지 않은 파일이 최근 15분 안에 바뀐 저장소는
`changes --json`에서 `busy`로 표시됩니다. 누가 작업 중이라는 뜻이므로 스킬은 새 커밋만 반영하고 초안은
다음 실행으로 넘기며, 검사도 이를 허용합니다. 페이지는 외부 작업처럼 로그인한
브라우저에서 읽습니다. 에이전트가 그 페이지에서 스크립트를 실행하고 결과를
`changes <이름> --input <파일>`로 넘기며, 돌려받은 항목의 id만으로 바뀌었는지 판단합니다.
진행 상황을 묻거나 아는 것을 근거로 글을 써 달라고 하면 `excudo-recall` 스킬이 바뀐 출처의
노드부터 갱신하고 `changes mark <이름>`으로 표시한 뒤, 메모를 근거로 답하고 근거로 쓴 노드를
밝힙니다. 지켜보는 출처는 읽기만 합니다. 지식의 줄에는 근거 등급(`확정:`, `관찰:`, `추정:`,
`제안:`, `대체됨:`)을 붙이며, 사용자의 결정은 `확정:`뿐입니다. 예약 실행에서는 바뀐 출처를 묻지 않고
모두 갱신하며, 확정할 수 없는 내용은 출처와 함께 `관찰:`이나 `추정:`으로 적습니다. 지식 노드는 사용자가 아니라
에이전트가 유지하므로 정리 후보에서 길이, 나이, 중복을 따지지 않습니다.

## 다른 앱의 메모 따라가기

몇몇 영역에 대한 지금의 생각을 휴대폰 메모 앱이나 공유 문서 같은 다른 앱의 메모 한 편에 적고 그곳에서
고쳐 가는 사람도 있습니다. `note` 출처는 그런 메모를 따라가고, `excudo-follow` 스킬이 메모에
반영합니다.

```js
sources: [
  { name: "thoughts", kind: "note", label: "생각 메모", url: "https://notes.example.com/n/1",
    between: "---", removed: "settle", script: async () => readTheNoteLineByLine() },
],
```

표식만 있는 줄(`between`, 정하지 않으면 `---`) 두 개 사이만 따라가며, 표식 쌍이 더 있으면 그만큼
영역이 늘어납니다. 빈 줄이 블록을 끝내고, 블록의 첫 줄이 그 블록의 머리말입니다. 메모에는 계정이나
번호 같은 다른 내용도 있을 수 있습니다. 그래서 `sources script`가 스크립트를 감싸서, 페이지 안에서
표식 사이를 자르고 개인 정보로 보이는 줄(비밀번호나 코드, 계좌, 카드, 전화, 신분증 번호, 라이선스 키,
토큰, 전자우편 주소, 숫자만 있는 줄)을 버린 결과만 브라우저 밖으로 나오게 합니다. 엔진은 받은 것을
한 번 더 거릅니다. `changes <이름> --input <파일>`은 마지막으로 표시할 때 git 밖의 캐시에 남긴 블록과
지금 영역을 블록 단위로 비교해 새 블록, 바뀐 블록, 지운 블록을 알리며, `sources.json`에는 지문만
남깁니다. 표식 쌍이 없는 메모는 `unmarked`이며, 생각을 모두 지운 메모로 보지 않고 표시도 하지 않습니다.

스킬의 `where.mjs`는 블록마다 그 머리말과 줄을 이미 담은 메모의 줄을 알려 줍니다. 메모가 이미 담은
생각은 그 자리에 합치고 보강하며, 아무 곳도 담지 않은 생각은 가장 가까운 노드의 줄이나 하위 노드로
만듭니다. 지운 생각은 사용자에게 묻고, `removed: "settle"`(지우면 끝났거나 폐기한 것이라고 사용자가
정한 경우)이면 메모와 기록이 보여 주는 대로 완료로 바꾸거나 메모에서 뺍니다. 스킬의 검사는 메모를
읽었다고 표시했는지, 모든 블록을 메모가 담는지, 지운 줄을 담은 열린 할 일이 남지 않았는지, 개인 정보로
보이는 줄을 넣지 않았는지 확인합니다.

## 요청에서 배우기

`conversations: true`이면 `requests`가 이 컴퓨터에서 Claude Code와 Codex에 입력한 요청을
읽습니다(`~/.claude/projects`, `~/.codex/sessions`. 다른 폴더는 `{ claude, codex, exclude }`로
지정합니다). 도구나 다른 에이전트가 끼워 넣은 글과, 에이전트를 거쳐 실행한 셸 명령(`! 명령`)과
그 출력은 거릅니다. Codex 음성 세션에서는 함께 넘어온 대화를 빼고 사용자가 말한 내용만 남기며, 세션을
끝낼 때 넘어오는 나머지 대화는 요청으로 보지 않습니다. 붙여 넣은 글은 따로 둡니다. 요청에는 `[pasted N]`으로 표시되고, 목록에는 붙여
넣은 글마다 길이와 앞부분이 나오므로 붙여 넣은 검토 결과나 명세를 사용자의 결정으로 읽지 않습니다.
요청마다 입력한 폴더의 노드가 붙습니다. 추출 방식이 바뀌면 로그를 다시 읽고, 로그가 지워진 요청은
캐시에서 다시 걸러 남깁니다. 원문은 작업 폴더의 기록 파일(`.excudo/records.db`, Node에 내장된 `node:sqlite`로 쓰는 SQLite 파일 하나)에만 남고 그래프와 git에는 들어가지 않습니다. 이전 버전의 JSON 파일은 한 번 옮긴 뒤 `*.imported`로 이름을 바꿉니다. 캐시가 그래프 안에
있거나 git이 무시하지 않는 자리에 있으면 `requests`는 실행하지 않습니다. 정리 인터뷰는
지난 정리 뒤의 요청에서 맡긴 일과 정한 결정을 찾습니다(`requests --for cleanup`).
`excudo-reflect` 스킬은 오래 갈 결정, 작업 방식, 바로잡은 내용을 찾아
(`requests --for reflect --candidates`) 후보를 `reflect.json`에 모으고, 기준을 넘은 것을
`interests` 노드 아래의 노드로 올립니다. 스킬이 한 일을 바로잡은 내용에는 그 스킬의 이름과
그 실수를 재현한 경우의 이름을 붙입니다. 그 스킬이 그 경우를 기록하거나([`skills mistake`](#스킬은-코드를-품습니다))
그 경우를 묻는 질문이 남을 때까지 회고의 검사가 실패합니다. 목적마다 읽은 위치를 따로 표시합니다
(`requests mark --for <목적> --until <시각>`). 예약 실행도 할 수 있으며, 그때는 판단이 필요한
것을 정하지 않고 질문으로 남깁니다. 예약 실행(`claude -p`)이 입력한 글은 그 실행의 프롬프트이지
사용자의 요청이 아니므로 뺍니다.

## 한 일을 기록하기

`activity`는 같은 로그에서 세션마다 한 일을 읽어 같은 기록 파일(그래프와 git 밖)에 둡니다. 날짜별 폴더와 시간, 사용자가 붙인 이름이나 도구가 만든 제목, 실행한
스킬, 그 검사의 통과 여부, 연 PR, 비용입니다. 사용자의 요청이든 에이전트의 답이든 입력된 글은
남기지 않습니다. 사용자의 커밋도 읽습니다. 저장소마다 설정된 작성자로 거르며, 작업 폴더의 저장소,
지켜보는 저장소, 노드의 경로 줄이 가리키는 폴더, 세션이 일한 폴더를 봅니다. 예약 실행(`claude -p`,
`codex exec`)은 예약 실행으로 표시하고, 그 실행이 저장소에서 일하는 동안 만든 커밋은 그 실행의
것으로 셉니다. 그날 아무것도 입력하지 않은 세션, 임시 폴더의 세션, 메모에서 다루지 않는 폴더의
세션은 뺍니다. 바뀌지 않은 로그는 다시 열지 않습니다.

뷰에서는 `activity` 펜스로 보여 줍니다.

````md
```activity
days: 14
```
````

빌드가 이 펜스를 최근 며칠의 기록으로 바꿉니다. 최근 날짜부터, 날짜마다 노드별로 세션, 커밋, PR을
다섯 개까지 보여 주고 나머지는 개수만 적으며, 그날의 예약 실행도 적습니다. 오늘만 펼쳐 둡니다.
검사는 알린 문제를 고친 뒤 다시 실행하므로, 세션마다 스킬 하나의 검사를 마지막 결과로 한 번만 셉니다. 모든 줄은 엔진이 쓴 문장입니다.
개인 정보로 보이는 제목은 가리고, 긴 커밋 메시지는 요지만 보여 주며, 제목 안의 링크, 태그, 속성
문법은 효력이 없게 바꿉니다. 저널에는 쓰지 않습니다. `activity show`는 뷰가 보여 줄 내용을
출력합니다.

`sessions [<노드>]`는 다시 이어 갈 세션을 찾습니다. 그 노드나 그 아래 노드에서 일한 세션(`--path`로
주면 그 폴더에서 일한 세션, 이전 경로와 새 경로 모두)을 최근 것부터 보여 주고, 세션마다 지금 폴더에서
이어 켜는 명령(`cd '<폴더>' && claude --resume '<id>'`나 `codex resume '<id>'`)을 붙입니다. 예약 실행은
뺍니다. 그사이 이름을 바꾼 폴더(`moved`)의 세션은 새 폴더에서 이어 켜며 그 사실을 알립니다. 폴더가
없어졌을 때, 그리고 Claude Code가 대화를 아직 이전 폴더의 저장소에 두고 있어서 새 폴더에서는 찾지
못할 때도 알립니다(`~/.claude/projects/<폴더 경로의 영문자와 숫자 밖의 글자를 -로 바꾼 이름>`).

## 한 목록을 여러 곳에서 같게 유지하기

어떤 목록은 여러 곳에 있습니다. 홈 위쪽의 계획, 매주 보는 파일의 한 구역, 웹 사이트가 고치는 보드, 휴대폰 앱의
메모가 그렇습니다. 미러는 이것들을 한 목록으로 유지합니다. `mirrors`에 위치를 적으면 `mirror`가 어느 위치에서
고친 것이든 합쳐 모든 위치에 씁니다.

```js
mirrors: [{
  name: "plans",
  places: [
    { page: "홈", section: "계획", tasks: true }, // `## 계획` 아래의 `- ### 주제` 블록, 항목은 할 일
    { export: "weekly", region: "계획" },         // 내보내기 파일의 직접 적는 구역: `### 주제`와 `- 항목`
    { board: "메모장" },                          // 웹 사이트의 보드가 고치는 페이지: `- 주제`, `\t- 항목`
    { note: "keep", item: "ㄴ " },                // note 출처의 표식 사이: 주제 줄과 그 아래 항목
  ],
}]
```

내보내기 위치에도 `item` 표식을 줄 수 있습니다. 예: `{ export: "weekly", region: "계획", item: "ㄴ" }`.
값은 앞뒤 공백을 지운 뒤에도 비어 있지 않은 문자열이어야 합니다.
미러는 목록 줄과 들여쓴 일반 줄의 항목을 읽을 때 앞뒤 공백을 지운 표식과 그 뒤 공백을 뺍니다.
예를 들어 `- parent` 아래의 `  ㄴchild`와 `  ㄴ child`는 모두 `child`라는 하위 항목이 됩니다.

깊이는 그대로이며, 쓸 때는 계속 `- text`를 씁니다. `item`이 없으면 표식도 글에 남습니다.

위치마다 같은 목록을 그 위치의 모양으로 보여 줍니다. 주제가 있고 그 아래에 항목이 있습니다. `tasks`를 준 페이지에서
항목은 할 일입니다. 새 항목은 `TODO`로 쓰고, 끝낸 항목은 목록에서 빠지되 페이지에는 남으며, 줄 끝의 링크는 그 페이지의
것으로 둡니다. 위치마다 지난번에 가졌던 목록을 기억하므로, 고친 것과 아직 따라오지 못한 것을 구별합니다. 서로 다른 줄을
고친 것은 모두 남고, 두 위치가 같은 줄을 고쳤으면 늦게 고친 쪽을 따르며 이른 쪽의 줄은 맨 아래 겹친 수정 항목에 남겨
사용자가 정리합니다. 처음 실행은 모든 위치의 목록을 합칩니다. 두 위치에 같은 주제(같은 낱말)가 있으면 없는 항목만 더하고,
항목은 위 항목들이 같을 때만 같은 항목으로 보고(같은 글의 항목 둘은 둘로 남음), 새 주제는 끝에 더하며, 나중에 더한 위치도 같은
방식으로 들어옵니다. 위치는 파일마다 하나입니다. 한 페이지의 두 절, 이름이 같은 페이지와 보드, 한 파일을 쓰는 두 내보내기는 받지
않습니다. 주제나 위 항목의 순서를 바꿔도 할 일의 상태와 링크는 그 할 일을 따라가고, 두 위치에서 같은 글의 항목을 함께 더하면 더 많이 더한 쪽의 개수만큼 남습니다. 다른 위치에서 주제의 이름을 바꾸거나
지우면, 페이지가 그 주제 아래에 둔 끝낸 항목은 그 자리에 오는 주제 아래에 남습니다.

최근 몇 분 안에 누가 쓴 페이지와 실행이 보류한 페이지나 파일(`EXCUDO_HOLD`)은 건드리지 않고, 메모가 멈춤 상태(`자동 실행::
멈춤`)이면 아무것도 쓰지 않으며 다음 실행을 기다립니다. 페이지에 커밋하지 않은 편집이 있으면 미러가 쓰기 전에 그것만 따로
커밋하고, 미러가 쓴 페이지는 한 커밋으로 남깁니다. 그 커밋이 실패하면 다음 실행이 미러가 쓴 내용을 커밋하고, 그 뒤의 편집은 따로 커밋되도록 남깁니다. 엔진은 다른
앱을 직접 다루지 않습니다. 작업 폴더가 읽은 메모를 주면(`--note keep=<파일>`, `changes`가 note 출처를 읽는 `{ markers,
blocks }` 모양) 결과에 그 메모가 가질 글(`notes.keep.lines`, `write`)이 나옵니다. 작업 폴더가 메모에 쓴 뒤에는
`mirror mark --wrote keep=<파일> --note keep=<파일>`로 쓴 줄(한 줄에 하나)을 그 메모의 기준으로 기록하고, 다시 읽은 메모가
그 줄을 가졌는지 알립니다. 메모에 그 밖의 것이 있으면 다음 실행이 고친 것으로 합칩니다. 쓰지 못한 메모는 가졌던 것이나 실행이
가져온 고침을 그대로 기억하므로, 다음 실행이 메모에 없는 줄을 사용자가 지운 것으로 읽지 않고 같은 고침을 두 번 가져오지도 않습니다. 표식이 정확히 둘이 아닌 메모는 읽지 않습니다.

다른 앱에 밖에서 쓰는 일은 안전하지 않을 때가 많습니다. 실제 클릭이 필요하거나, 사용자의 포커스를 가져가거나, 같은 메모에 다른
글이 함께 있기 때문입니다. 그래서 실행마다 메모가 가질 글을 함께 남기고, `mirror text [이름] [출처] --copy`가 그 글을 클립보드에
넣습니다. 사용자는 그 글을 메모의 표식 사이에 붙여 넣으며, `--copy`를 빼면 글을 출력합니다. 붙여 넣기가 늘 쓸 수 있는 방법이고,
메모에 직접 쓰는 작업 폴더의 도우미도 안전하게 쓸 수 없을 때 이 방법으로 넘기면 됩니다. 다음 실행은 붙여 넣은 글이 예전에 준비한
글이어도 알아보므로, 늦게 붙여 넣어도 그사이 다른 위치에서 바뀐 것을 되돌리지 않습니다. 붙여 넣은 뒤 고친 것은 평소처럼 고침으로 합칩니다.

## 예약 실행

예약 실행(회고, 스킬 관리, 출처 수집)은 사용자가 메모를 고치는 동안 메모를 바꾸면 안 됩니다.
`save`, `snapshot`, `ingest`, `archive`는 그래프 잠금(`.excudo/graph.lock`) 하나를 함께 쓰므로
두 명령이 동시에 커밋하지 않고, 나중 명령은 1분까지 기다립니다. 예약 실행은 시작하기 전에 `idle`로
시작해도 되는지 확인합니다. 메모를 쓰는 곳이 없으면 종료 코드 0, 다른 명령이 잠금을 쥐고 있거나
커밋하지 않은 그래프 파일이 최근 몇 분 안에 바뀌었으면 1(`--minutes`, 기본 10분. 휴대폰에서
동기화된 편집도 셉니다), 일시 정지 줄이 있는 페이지가 있으면 3입니다.

```md
- 자동 실행:: 멈춤
```

어느 기기에서든 아무 페이지에 이 줄을 쓰면 모든 예약 실행이 멈추고, 지우면 다시 돕니다. 영문 작업
폴더는 `automation:: paused`로 쓰며, 어느 언어의 줄이든 모두 알아봅니다. `--json`은 어떤 파일과
페이지 때문에 기다리는지 알려 줍니다.

커밋하지 않은 생성 페이지(저장이 도중에 멈춰 남은 것)는 편집으로 세지 않습니다. 기다리지 않고 진행하려는
예약 실행은 다른 곳에서 고치는 중인 파일을 보류할 수 있습니다. 그 파일을 `EXCUDO_HOLD`에 한 줄에 하나씩
작업 폴더 기준 경로로 적으면(폴더는 그 안의 파일 전체) `idle`은 그 파일을 기다리지 않고, `save`와
`snapshot`은 어느 커밋에도 그 파일을 넣지 않으며, 스킬의 검사도 그 파일을 저장하라고 하지 않습니다. 예약
실행은 그 편집 전의 상태로 메모를 기록하고, 편집은 그 자리에 남아 따로 커밋됩니다. 메모를 쓰는 명령은 보류한
페이지를 건드리지 않고 그 일을 다음 실행으로 넘깁니다. 생성은 그 페이지의 생성 구역을 건너뛰고, 출처 수집은 그
페이지에 넣을 항목을 받지 않고 완료 처리도 하지 않으며, 작업 큐 보고는 기다립니다. `archive`는 그 페이지의 끝난 항목을
옮기지 않고(완료 노드가 보류되면 아무것도 옮기지 않음), 웹 사이트에서 온 변경은 묶음을 열어 둔 채 기다리며, 스킬 관리는
보류한 스킬(폴더 안의 파일 하나라도)을 그대로 둡니다. 보류한 페이지의 오류는 다른 페이지의 저장을 막지 않습니다. 방금 더하거나
지우거나 이름을 바꾼 페이지도 폴더의 시각으로 고치는 중인 편집으로 보며, 이름을 바꾸면 두 이름을 함께 봅니다.

고치다 멈춘 편집은 고치는 중이 아니라 끝난 편집으로 볼 수 있습니다. `idle --settle N`은 커밋하지 않은 편집을
나눕니다. N분 동안 아무도 건드리지 않았고 그 파일이 검사를 통과하면 오래된 것이라도 `settled`이고, 나머지는
`recent`입니다. 제목이 깨진 것처럼 반쯤 쓴 페이지는 아무리 오래 그대로여도 `settled`가 되지 않습니다. `--minutes`
안이면 `recent`이고, 그보다 오래되면 `unsettled`라서 예약 실행이 기다리지 않고 보류만 합니다. 검사하는 동안 바뀌거나 새로 바뀐 파일은
고치는 중으로 보고, 검사가 폴더에 낸 오류(페이지 없이 남은 하위 폴더)는 그 페이지와 폴더 안의 파일을 `settled`에서 빼며, 이름을 바꾼 두 경로는 함께 정해집니다. `snapshot --settle N`은 그래프 잠금을 쥔 채 `settled`
편집을 가려 검사가 읽은 내용 그대로 따로 커밋하고(그사이 편집기가 쓴 내용은 작업 트리에 남음), 일시 정지 줄이 있으면 커밋하지 않으므로, 예약 실행은 그 뒤 그 페이지도 평소처럼 처리하고 `recent`와 `unsettled`만 보류합니다. 그래서 몇 분 전에 멈춘 편집은 다음 실행이 아니라 이번 실행이 처리하고, 오래 커밋하지
않은 편집은 실행의 커밋에 섞이지 않고 따로 커밋됩니다. N은 휴대폰의 편집이 동기화되는 시간보다 길게 잡습니다.

예약 실행의 단계마다 `runs add <단계> --status ok|failed|deferred|paused`로 결과를 기록합니다.
`--reason`에 이유를 적습니다. `runs`는 최근 7일을 최신순으로 보여 주며, `--days N`으로 기간을 바꿉니다.
`--step <이름>`은 여러 번 써서 단계를 고릅니다.

`--failed`는 실패, `--deferred`는 보류한 실행을 고릅니다. 둘을 함께 쓰면 어느 쪽이든 고릅니다.
글 출력의 이유는 160자까지이며, `--full`로 전체를 봅니다.
`--json`은 기존 필드와 이유 전체를 그대로 내며, 같은 필터를 적용합니다.

`backup <폴더>`는 캐시의 일관된 사본(기록, 빌드 보호 기록,
따라가는 메모)을 씁니다. 에이전트는 오래된 로그를 지우므로 기록 파일이 요청의 유일한 사본일 수 있습니다.
예약 실행과 함께 백업합니다. 사본에는 요청 원문이 들어가므로 폴더는 캐시와 그래프 밖에 있고, 링크를 거치지
않으며, git이 무시하는 곳이어야 합니다. 같은 폴더에 다시 백업하면 새 사본을 다 쓴 뒤에 기록을 바꿉니다.

## 에이전트에게 일 맡기기

열린 할 일에 `#에이전트`(영문은 `#agent`, 또는 `queue: { tag }` 설정)를 붙이면 에이전트에게 맡긴 일이
됩니다. `queue`는 맡긴 할 일마다 에이전트가 사용자처럼 고르는 데 필요한 것을 함께 보여 줍니다. 그
할 일이 있는 노드와 요약, 노드나 가장 가까운 상위 노드의 경로 줄이 가리키는 작업 폴더, 그 노드와
상위 노드의 `방침:` 줄, 할 일 아래에 이미 있는 줄입니다. `excudo-queue` 스킬은 처리 대기인 할
일을 실행마다 `queue: { limit }`개(기본 2개)씩 맡아 읽기만 해서 알아보고, 보고서를 캐시
(`.excudo/reports/`)에 쓴 뒤 할 일 아래에 남깁니다.

```md
- TODO 새 가이드의 링크 확인 #에이전트
	- WAITING 검토: 링크 두 개가 지운 페이지를 가리킵니다. 고칠 방법은 보고서에 있습니다 [보고](file:///…)
```

그러면 할 일은 사용자를 기다립니다. 보고 아래에 답을 적으면 다시 처리 대기가 되어 다음 실행이 이어서
처리하고, 끝났으면 할 일을 닫거나 태그를 뗍니다. 에이전트는 맡긴 할 일을 완료로 바꾸지 않고, 작업
폴더의 파일을 고치거나 무엇을 보내지 않으며, 그런 일은 보고서에서 제안합니다. 스킬의 검사는 맡은 할
일마다 보고와 보고 파일이 있는지, 개인 정보로 보이는 내용이 메모에 들어가지 않았는지 확인합니다.

## 현황 보기

뷰에 `status` 펜스를 두면 메모 주변의 일이 어떻게 되고 있는지 보여 줍니다. 최근 며칠(기본 `days: 7`)의
예약 실행 단계와 마지막 결과, 에이전트에게 맡긴 할 일(처리 대기와 검토 대기), 최근 30일 동안 스킬마다
쓴 횟수와 검사 결과(통과보다 실패가 잦은 스킬은 표시), 외부 출처를 마지막으로 읽은 때, 회고가 남긴
질문 수입니다.

````md
```status
days: 7
```
````

`skills status`와 `skills upkeep`도 학습 스킬의 검사 결과를 같이 보여 주며, 최근에 에이전트가 쓴 스킬은
요청 문구와 상관없이 쓰이는 것으로 봅니다.

## 스킬은 코드를 품습니다

여기서 말하는 스킬은 프롬프트를 줄여 둔 것이 아니라, 작업의 일부를 매번 같은 방식으로 수행하는
코드를 품은 것입니다. 스킬 폴더에는 `SKILL.md`와 `scripts/`가 있고, 적어도 `scripts/check.*`와
`scripts/check.cases.json`이 있어야 합니다. 검사는 스킬의 요구 사항을 충족했는지 알리고(종료 코드
0 또는 1, 자세한 내용은 `--json`), 경우 파일에는 통과해야 하는 경우와 실패해야 하는 경우가 있습니다.
`skills lint`가 경우마다 facts를 검사에 직접 넘기고(`--facts <파일>`) 종료 코드를 보므로, 실패할 수
없는 검사는 걸러집니다.

경우는 동시에 실행하며, `EXCUDO_CASE_JOBS`로 동시 실행 수를 정합니다(1이면 순차 실행).
기본값은 CPU 병렬 처리 수에 따라 최대 8이며, 기대와 다른 결과는 혼자 재검사하고 도우미가 실패하면 모두 순차 실행합니다.

매번 같은 결과가 나와야 하는 검색과 변경은 `SKILL.md`가 실행하는 다른
스크립트에 둡니다. 스킬은 필수 검사를 모두 통과해야 하고, 품질 기준으로 0점부터 100점까지 점수를 받습니다.

| 기준 | 점수 | 확인하는 것 |
| --- | --- | --- |
| 필수 | — | 폴더 이름과 설명이 있는 `SKILL.md`, 스크립트, `scripts/check.*`, 경우를 예상대로 판정함(통과해야 하는 경우와 실패해야 하는 경우가 하나 이상씩), `SKILL.md`가 모든 스크립트를 실행하고 가리킨 스크립트가 모두 있음, 스크립트 문법, 남은 `FILL IN:` 표시 없음, 특정 에이전트만 아는 도구 호출 없음, 비밀 값 없음, 학습 스킬이면 요청 문구를 옮겨 적지 않고 사용자가 지적한 실수로 기록한 경우가 모두 실패해야 하는 경우로 남아 있음 |
| `runs-check` | 25 | `SKILL.md`가 명령 블록에서 검사를 실행함 |
| `triggers` | 20 | 설명이 스킬을 언제 쓰는지 밝힘 |
| `usage` | 20 | 스크립트마다 맨 위에 사용법이 있음 |
| `portable` | 20 | 이 컴퓨터의 홈 폴더 경로가 없음 |
| `size` | 15 | `SKILL.md`가 500줄 이하이며 따라 할 만큼의 내용이 있음 |

작업을 저장했는지 보는 검사는 그래프 전체를 봅니다. `--only <페이지>`를 주면 `save --only`로 저장한
페이지만 보므로, 다른 사람이 다른 곳을 쓰는 중에도 통과합니다.

스킬로 한 일에서 사용자가 지적한 실수는 그 뒤로 검사가 잡습니다. 에이전트는 일을 고치면서 그 스킬의
검사가 그 실수를 실패로 판정하게 하고, 실수를 재현한 경우(`expect: "fail"`)를 더합니다. 학습 스킬이면
이어서 `skills mistake <이름> --case "<경우>" --why "<요약>"`을 실행합니다. 이 명령은 그 경우가 fail을
기대하고 검사가 지금 그 경우를 실패로 판정할 때만 `skills.json`에 기록하며, 요청 문구를 옮긴 요약은
받지 않습니다.

lint는 기록된 경우를 계속 지킵니다. 그 경우를 지우거나 통과하는 경우로 바꾸면 lint가
실패하고, `upkeep`은 경우를 되살릴 때까지 그 스킬을 쓰지 않도록 합니다. `skills status`는 스킬마다
검사가 지키는 실수의 수를 보여 주고, 회고는 그런 교정을 찾았는데 아직 기록되지 않았으면 사용자에게
묻습니다. 엔진 스킬의 실수는 엔진에 고칠 점으로 알리며, 엔진에서 그 스킬 검사의 실패하는 경우가
됩니다. 모든 작업 폴더의 `AGENTS.md`에 이 규칙이 있습니다.

엔진의 스킬은 모두 100점이며 테스트가 이를 지킵니다. `conversations`를 켠 작업 폴더는 요청에서
스킬도 배웁니다. `skills candidates`는 비슷한 말(세 글자 조각으로 비교하므로 영어뿐 아니라
한국어도 됩니다)로 `windowDays` 안에 `minSessions`개 세션에서 `minRequests`번 이상 되풀이된 요청을
묶습니다.

`excudo-skills` 스킬이 후보를 하나씩 읽고, 대화나 한 번뿐인 일은 제외하며
(`skills dismiss <id> --reason …`), 되풀이되는 작업을 스킬로 만듭니다. 뼈대 스크립트가
`skills/<이름>/`을 만들고 에이전트가 절차와 검사를 채우면, `skills lint`가 점수를 매기고
`skills adopt <이름> --from <후보>`가 규칙과 `minScore`(기본 80)를 충족한 스킬을 설치합니다.
충족하지 못한 스킬은 초안으로 남습니다.

`skills upkeep`은 학습한 스킬을 검사하고 설치본을 갱신하며, 요청을 세고 휴면 스킬을 알립니다.
알려진 경우에서 시간이 초과되거나 네트워크, 인증 오류만 나면 판정할 수 있는 실행이 올 때까지 보류합니다.
일반 판정이 틀리거나 점수가 `minScore`보다 낮으면 그 스킬을 쓰지 않도록 합니다.
누가 고친 설치본은 그대로 두고 알립니다.
`skills retire <이름>`은 사용을 멈추며, `skills adopt <이름> --force`는 고친 설치본도 바꿉니다.

예약 실행이 의존하는 스킬은 `skills: { keep: ["release-notes"] }`에 적습니다.
관리 명령은 목록의 스킬을 내리거나 퇴역시키지 않습니다.
검사가 실패하면 설치를 유지하고, 실패한 검사와 `state: "held"`를 알린 뒤 종료 코드 1을 냅니다.
글과 JSON 출력 모두 같은 종료 코드를 냅니다. 검사를 고친 뒤 다시 관리합니다.

기록을 바꾸는 명령은 서로 기다립니다. `skills.json`은 스킬과 제외한 후보를 요청 키, 건수, 날짜로만
기록하고 요청 원문은 담지 않으며, `save`가 스킬 원본과 함께 커밋합니다. 스킬이나 `reflect.json`이
에이전트에게 입력한 문구를 git에 넣게 되면 `save`는 커밋하지 않습니다.

스킬은 그 작업을 하는 곳에 둡니다. 작업 폴더 자체의 일을 하는 스킬은 작업 폴더에 설치합니다. `.agents/skills/<이름>`과
`.claude/skills/<이름>`이 원본을 가리키며, `save`가 이 연결도 커밋합니다.

다른 폴더에서 하는 일을
맡는 스킬은 그 폴더가 저장소 하나뿐이더라도 `--global --why <이유>`로 어느 폴더에서나 쓰게 합니다.
사용자가 요청했다면 `--requested`를 씁니다. 설정이 `install: "global"`이 아닌데 둘 다 없으면 `adopt`는
스킬을 작업 폴더에 둡니다. 작업 폴더만의 일은 설정이 `install: "global"`이어도 `--workspace`로 작업 폴더에
둡니다. 전역에 두는 스킬은 `~/.agents/skills/<이름>`에 복사해서 원본을 밝힌
`SOURCE.md`를 두고 `~/.claude/skills`와 `~/.codex/skills`에서 연결합니다.

연결 Git 워크트리에서도 전역 설치본을 그 워크트리의 스킬 원본과 비교할 수 있습니다.
자체 설치 기록이 없으면 소유 체크아웃의 기록을 읽습니다.
설치본의 설치, 갱신, 삭제는 소유 체크아웃에서 실행합니다. 연결 워크트리는 설치본을 바꾸지 않습니다.

어느 작업 폴더에서나 하는
메모 작업은 엔진의 스킬에 맡기고, 에이전트의 기본 명령이 이미 하는 일은 스킬로 만들지 않습니다.
`upkeep`은 스킬마다 요청을 입력한 폴더를 알려 줍니다. 이 스킬의 검사는 작업 폴더에 두었지만 요청이
대부분 다른 폴더에서 나온 스킬을 찾아냅니다. 그런 스킬은 정작 그 폴더에서 읽히지 않기 때문입니다.
반대로 전역에 두었지만 요청이 모두 이 작업 폴더에서 나왔고 다른 폴더에 둘 이유도 없는 스킬도 찾아냅니다.

스킬은 채택한 자리에 그대로 남고, `--workspace`로 작업 폴더에 되돌릴 수 있습니다. 이 스킬을 예약 실행하면 사람 없이도 이어집니다. 예약 실행에서는 확실히 맞는 스킬만
만들어 채택하고 나머지는 사용자에게 남깁니다.

## 노드의 작업 폴더

노드는 일하는 폴더를 경로 줄로 적을 수 있습니다. 목록 항목이나 제목 아래 문단으로
`` `/Users/me/work/site` ``처럼 씁니다. `workspaces`는 브랜치를 git에서,
창 이름은 에이전트가 `--input`으로 넘긴 내용(`{ path, branch?, labels? }`의 JSON 목록, 예를 들어
터미널 앱에서 내보낸 것)에서 갱신합니다. 없어진 폴더는 `workspace-gone` 질문이 될 뿐 일을 끝내거나
지우지 않습니다. 그 폴더에서 입력한 요청은 그 노드에 붙습니다.

여러 작업이 한 폴더에서 진행되면(여러 일이 함께 쓰는 기본 체크아웃 등) 그 폴더는 공유 폴더입니다.
그 폴더에서 일하는 노드마다 경로 줄을 두고 그 작업의 창만 적으며, 이 노드들은 한 상위 노드 아래에
둡니다. `workspaces`는 줄마다 그 줄의 창을 유지하고, 어느 줄에도 없는 창을 알립니다(`unassigned`).
그 폴더에서 입력한 요청은 상위 노드에 붙습니다. 서로 다른 맨 위 노드 아래의 노드들이 같은 폴더를 적거나
(`path-duplicate`), 두 노드의 줄이 같은 창을 적으면(`path-window-twice`) `check`가 경고합니다.
`--input`이 앱에서 쓰는 작업 폴더 이름(`name`)을 함께 넘기면 `workspaces`는 메모가 정하는 이름도
알립니다(`names`). 폴더를 적은 노드의 이름이고, 공유 폴더는 가장 가까운 공통 상위 노드의 이름이며,
자기 폴더가 여럿인 노드는 노드 이름에 폴더 이름을 붙입니다. 이름은 앱에서 바꾸고, 엔진은 알리기만
합니다.

폴더 이름을 바꾸거나 옮기면 `moved`에 이전 경로와 새 경로를 적습니다(`{ "~/old/site": "~/work/site" }`).
그러면 이전 폴더에서 입력한 요청이 새 폴더의 노드에 붙고, `workspaces`는 이전 폴더를 적은 경로 줄을
질문으로 남기지 않고 새 경로로 고칩니다. 작업 폴더 자신을 옮겼다면 이전 폴더에서 전역에 설치한 학습
스킬도 계속 이 작업 폴더의 것으로 보고, 다음 관리에서 새 폴더를 적어 다시 설치합니다. 내보내기가 쓴 파일도
계속 엔진이 쓴 파일로 봅니다. 폴더와 함께 옮긴 Claude Code 대화 저장소에서는 이미 읽은 요청을 다시 읽지 않습니다. 메모에서 추적하지 않는 폴더는 `workspaces untrack <폴더>`로
`review.json`에 기록합니다. 그 안의 작업 폴더는 더 묻지 않고, 그 폴더의 요청에는 `untracked`가
붙습니다. `workspaces track <폴더>`로 되돌립니다.

## 사용자의 형식으로 파일 유지하기

내보내기는 엔진이 메모로 쓰는 파일입니다. 그래프 밖에 두며, 메모 옆에 두는 간단한 할 일 목록처럼
사용자가 예시로 보여 준 형식을 따릅니다. `build`와 `save`가 실행될 때마다 이 파일을 다시 쓰므로 저장한
변경이 모두 반영되고, 아웃라이너에서 메모를 고친 뒤에는 `export`로 다시 씁니다. 일을 바꾸는 곳은
메모 하나뿐입니다. 쓴 뒤 누가 직접 고친 파일은 그대로 두고 알리며(`export --force`로 바꿀 수
있습니다), 엔진이 쓰지 않은 파일도 그대로 둡니다.

```js
exports: [{
  name: "todo",
  file: "todo.md",            // 작업 폴더 기준이나 ~/…. 그래프 안에는 둘 수 없습니다
  retitle: ["board"],         // 그 일을 나타내는 제목을 붙일 items 출처
  sections: [
    { heading: "- 지금", states: ["DOING"], line: "{title}" },
    { nodes: ["요청"], keyed: true, without: ["언젠가"],
      line: "- [{key}] {title} {links}", child: "  - {title} {links}", gap: 1 },
  ],
}],
```

구역은 `states`, `nodes`(그 노드와 아래), `keyed`(items 출처의 `key`를 이름으로 단 링크), `tags` 중
하나라도 맞는 열린 할 일을 모으고, 아무것도 정하지 않으면 열린 할 일을 모두 모읍니다. `without`에 적은
이름을 언급하거나 그 노드 아래에 있는 할 일은 뺍니다. 저널은 읽고 지식 노드는 읽지 않습니다. 줄
템플릿에는 `{title}`, `{key}`, `{keys}`, `{link}`, `{links}`, `{state}`, `{node}`를 쓰고, `child`는 할 일
아래의 메모와 열린 항목을 씁니다. 출처에서 가져온 제목은 양식 이름인 경우가 많습니다. `export`는
`retitle` 출처의 할 일 가운데 아직 그런 제목을 쓰는 것을 알려 주고, `excudo-export` 스킬이 항목을
읽어 메모에 그 일을 나타내는 짧은 제목을 붙입니다. 이 스킬은 사용자의 예시로 내보내기를 설정하기도
하며, 검사는 파일마다 최신인지, 제목을 붙였는지, git이 무시하는지, 저장했는지 확인합니다.

구역은 사용자가 정한 항목의 순서를 지킬 수 있습니다. `order: "file"`을 주면(엔진이 파일에서 그 구역을 찾도록
제목이 있어야 합니다) 다시 쓸 때마다 파일에 있는 순서대로 항목을 씁니다. 파일에 아직 없는 할 일은 끝에 붙이고,
더는 모으지 않는 할 일은 뺍니다. 항목의 자리만 옮긴 것은 직접 고친 것으로 보지 않으므로 다음 빌드가 그 순서를
지키며, 항목의 글을 고친 것은 전처럼 직접 고친 것으로 봅니다. `deadline`은 `DEADLINE:`이 있는 할 일 아래,
메모 줄 다음에 한 줄을 씁니다. 템플릿에는 `{date}`(`2026-10-27`), `{year}`, `{month}`, `{day}`(`10`, `27`)를
씁니다: `deadline: "  - 기한 {month}/{day}"`.

한 할 일을 파일의 한 곳에서만 이어 갈 수 있습니다. `once: true`를 준 구역은 파일의 위쪽(앞선 구역이나 포함한
파일)에 키나 링크가 이미 나온 할 일을 쓰지 않습니다. 맨 위에 다른 도구가 쓰는 보고가 진행 중인 일을 맡으면, 아래
목록에는 보고에 없는 일만 남습니다. 보고에서 빠진 할 일은 다음에 다시 쓸 때 목록으로 돌아옵니다.

할 일을 모으지 않는 구역도 두 가지 있습니다. 직접 적는 구역(`{ heading: "## 메모", keep: "메모" }`)은
사용자가 쓰는 곳입니다. 엔진이 그 앞뒤에 주석 줄(`<!-- 메모 -->`, `<!-- 메모 끝 -->`)을 쓰고, 파일을 다시
쓸 때마다 두 줄 사이의 내용을 그대로 옮기므로 직접 적는 구역 밖을 고쳤을 때만 직접 고친 파일로 봅니다. 두
주석 줄은 지우지 않습니다. 그 줄이 없는 파일은 직접 고친 파일로 보고 다시 쓰지 않습니다. `pad`(0~3,
`{ keep: "메모", pad: 1 }`)를 주면 두 주석 줄 안쪽에 그만큼 빈 줄을 두어, 구역에 글을 쓰다가 주석 줄을
건드리지 않게 합니다. 다시 쓸 때는 직접 적은 내용의 앞뒤 빈 줄을 떼고 pad만큼 다시 붙이며, pad를 바꿔도
직접 고친 파일로 보지 않습니다. 직접 적는 구역에는 제목이 없어도 됩니다. 포함 구역(`{ heading: "# 이번 주",
include: ".state/week.md" }`)은 작업 폴더의 다른 도구(예약 실행이 부르는 스크립트 등)가 쓴 파일을 그대로
넣으며, 그 파일이 아직 없으면 제목만 씁니다.

## 메모를 웹 사이트로 보기

엔진은 메모를 cudoc-export로 웹 사이트로 쓸 수 있습니다. Tine이 없는 곳, 즉 컴퓨터의 브라우저,
휴대폰, 정적 호스팅에서 읽기 위해서입니다. 노드마다 한 페이지가 되고 페이지 끝에는 그 아래 노드의
접히는 트리가 붙습니다. 홈과 생성 뷰도 페이지가 되며, `{{query}}`는 사이트를 만들 때의 결과로
바뀝니다. 저널은 설정하면 들어갑니다. `[[페이지]]`는 링크가 되고, 할 일은 상태가 보이는 체크박스가
되며, `DEADLINE:`은 할 일 옆의 날짜가 되고, 아웃라이너 자신의 속성(`collapsed::`, `id::`)은
빠집니다. 웹 사이트는 줄마다 메모의 주소(`data-excudo-page`, `data-excudo-line`)를 지니므로, 도구가
페이지의 줄에서 파일로 되돌아갈 수 있습니다.

```js
site: {
  out: ".excudo/site",   // 작업 폴더 기준이나 ~/…. 그래프 밖이며 통째로 바꿔 씁니다
  title: "내 메모",       // 정하지 않으면 작업 폴더 이름
  mode: "site",          // "standalone"이면 홈 한 쪽에 모든 것을 담아 보낼 수 있습니다
  open: 0,               // 노드 트리를 처음에 펼쳐 두는 깊이. 정하지 않으면 접습니다
  journals: false,       // 저널을 저널 페이지 아래에 넣습니다
  css: [],               // 엔진의 스타일 다음에 읽을 스타일시트
  onSave: true,          // build와 save도 웹 사이트를 씁니다. false면 site만 씁니다
},
```

내보내기 도구는 한 번만 설치합니다(`CUDOC_SKIP_BROWSER_DOWNLOAD=1 npm install cudoc-export@^1.0.0`,
엔진은 웹 사이트를 쓸 때만 읽습니다). 그다음 `excudo site`를 실행하고, `--open`을 붙이면 홈을 엽니다.
페이지의 절(쿼리 결과, 노드 아래 트리)은 접힌 채 시작하므로 페이지를 제목부터 읽습니다. 페이지마다
작은 런타임이 노드를 검색하고 홈에 마지막으로 본 페이지를 보여 줍니다. 옆의 문서 목록은 넓은 화면에서
지금 페이지까지의 경로만 펼칩니다. 좁은 화면에서는 목록이 페이지에서 빠지고, 떠 있는 버튼이 목록을
페이지 위의 패널로 접힌 채 엽니다. 패널은 바깥을 누르거나 Esc를 누르거나 링크를 따라가면 닫힙니다.
목록의 버튼으로 모두 펼치거나 접을 수 있습니다. 연 상태는 기기마다 기억합니다. 런타임은 서버가 필요
없고, 페이지의 정책은 웹 사이트 자신의 받는 곳(아래 절)만 허용합니다.
`check`는 웹 사이트가 보여 줄 수 없는 쿼리를 알립니다(`query-unsupported`). 읽는 형태는 `and`, `or`,
`not`, `task`, `[[페이지]]`, `"글"`, `(page "이름")`입니다. 폴더를 어디로 보낼지는 사용자가 정하며,
다음 절처럼 엔진이 사용자의 로그인으로 지키는 곳에 올릴 수도 있습니다.

### 내 로그인으로만 여는 곳에 올리기

명령 하나로 웹 사이트를 Vercel에 올립니다. 사용자의 Vercel 로그인으로만 열리며, 휴대폰으로 열 코드도
보여 줍니다.

```sh
npx --no-install excudo site setup
```

없는 것(내보내기 도구, Vercel CLI)을 설치하고 웹 사이트를 씁니다. 그다음 브라우저에 Vercel의 기기
로그인을 열고, 사용자가 그곳에서 허용할 때까지 기다립니다. 프로젝트를 만들어 연결하고(폴더 이름에
`-memo`를 붙인 이름, 또는 `--project <이름>`), Vercel Authentication이 production 주소를 포함한 모든
배포를 지키게 한 뒤 올립니다. 끝으로 주소를 열고 복사하며 코드를 보여 줍니다. 무료 Vercel 계정으로
충분하며, Vercel의 Hobby 플랜은 개인 용도입니다. 다시 실행하면 이미 된 단계는 건너뜁니다.

그 뒤로는 `excudo site publish`가 웹 사이트를 쓰고 바뀐 것이 있을 때 올립니다. 보호 범위가 모든
배포보다 좁으면 올리지 않고, 사용자가 먼저 할 일이 있으면 75로 끝나므로 예약 실행이 불렀다가 나중에
다시 할 수 있습니다. `excudo site open`은 주소를 코드와 함께 다시 열고, `excudo site status`는 로그인,
프로젝트, 보호, 마지막 배포를 보여 줍니다. 로그인은 CLI가 스스로 지닙니다. 엔진은 인증 정보를
입력하거나 저장하지 않고, 배포에 마지막 커밋의 메시지와 작성자가 함께 가지 않도록 git을 가립니다.

호스트 조회는 60초, 배포와 setup의 패키지 설치는 10분 안에 끝냅니다.
`EXCUDO_HOST_TIMEOUT`은 조회 제한을, `EXCUDO_DEPLOY_TIMEOUT`은 배포 제한을 초 단위로 바꿉니다.
게시나 이슈 읽기, 닫기가 네트워크, 프록시 문제로 실패하면 75로 끝나며 다음 실행에서 다시 시도합니다.
연결 실패를 로그인 해제로 안내하지 않습니다.

웹 사이트가 같고 24시간 안에 모든 배포의 보호를 확인했으면 호스트를 호출하지 않습니다.
24시간이 지나거나 `--force`를 쓰면 배포 전에 보호와 받는 곳의 토큰을 다시 확인합니다.
Vercel에서 토큰을 바꾼 뒤 바로 배포하려면 `--force`를 씁니다.

`site status`는 저장된 주소, 마지막 배포와 받는 곳의 토큰 시각을 먼저 보여 준 뒤 실시간으로 조회합니다.
상태 조회는 호출마다 10초로 제한하고 연결 불가를 표시하며, JSON에는 `reachable: false`를 담습니다.
웹 사이트의 GitHub 요청은 8초로 제한하고, 페이지는 실패한 이슈 조회를 나중에 다시 시도합니다.

```js
site: {
  publish: {
    project: "my-memo",          // Vercel 프로젝트. 정하지 않으면 폴더 이름에 -memo를 붙입니다
    dir: ".excudo/publish",      // Vercel이 받는 폴더. 웹 사이트와 그 설정만 둡니다
    open: ["node", "tab.mjs"],   // 링크를 마지막 인자로, EXCUDO_LINK=login|site|dashboard와 함께 엽니다. 기본은 브라우저
    close: ["node", "tab.mjs", "close"], // open이 처음 출력한 줄로 로그인 페이지를 닫습니다
    copy: true,                  // 주소를 열 때 복사합니다
  },
},
```

### 웹 사이트에서 할 일의 상태 바꾸기

받는 곳을 설정하면 페이지의 할 일 상태가 버튼이 됩니다. 누르면 TODO, DOING, WAITING, DONE, CANCELED(하지
않기로 한 일) 가운데 하나를 고르고, 체크박스를 체크하면 DONE이 됩니다. 고른 상태는 바로 보이고, 메모에 반영될 때까지
표시를 단 채 기기에서 기다립니다. 0.5초 안에 웹 사이트 자신의 함수(`api/edit`, `site publish`가
페이지 옆에 둡니다)에 가고, 함수는 묶음마다 사용자의 비공개 GitHub 저장소에 이슈 하나를 만듭니다.
이슈에는 줄의 주소와 상태만 있고 할 일의 글은 없습니다(아래 홈 보드를 저장한 것만 이슈에 글이 남습니다).

페이지는 메모가 아직 받지 않은 변경도 함수에 묻습니다. 열 때, 다시 화면에 나올 때, 기다리는 변경이
있는 동안 30초마다 묻습니다. 그래서 휴대폰에서 고른 상태가 컴퓨터에서도 보이고, 메모가 받은 변경은
다음 웹 사이트가 그대로 보여 줄 때까지 체크 표시와 함께 보입니다. 기다리는 변경이 있으면 상태 줄에
'지금 반영' 버튼이 나옵니다. 누르면 요청 이슈를 남기고(`api/sync`), 그 이슈를 자주 확인하는 컴퓨터가
평소 간격을 기다리지 않고 바로 가져옵니다.

설정 한 줄을 더하고 설정 명령을 다시 실행하면 켜집니다. 명령은 멈춘 곳부터 이어 갑니다.

```js
site: {
  inbox: true,   // 저장소를 지정하려면 { github: { repo: "me/memo-inbox" } }, 직접 만든 예약 실행이
                 // site pull을 부르면 schedule: false
},
```

```sh
npx --no-install excudo site setup
```

설정 명령은 GitHub CLI(`gh`, macOS에서는 Homebrew로 설치)로 GitHub에 로그인합니다. 로그인 페이지를 열고
코드를 복사해 둡니다. 그다음 받는 곳의 비공개 저장소(`<계정>/<프로젝트>-inbox`)를 만들고 페이지 두 개를
엽니다.

값이 채워진 GitHub 페이지에서 Repository access로 그 저장소를 고르고, 토큰을 만들어 복사합니다.
Vercel 페이지에서 `EXCUDO_INBOX_TOKEN`을 Production으로 더하고 값에 토큰을 붙여 넣은 뒤 저장합니다. 설정
명령은 변수가 보일 때까지 기다렸다가(이름만 읽고 값은 읽지 않습니다) 사이트를 올립니다. macOS에서는
`site pull`을 1분마다 예약하고, 다른 곳에서는 예약 도구에 넣을 명령을 알려 줍니다. 나중에 토큰을 바꾸면
다음 배포가 알아채고 다시 올립니다.

`excudo site pull`이 변경을 가져옵니다. 받는 곳의 열린 이슈를 읽어 5분마다 가져오고, 페이지가 요청했거나
`--now`를 붙이면 바로 가져옵니다. 그 페이지에 남은 사용자의 편집은 먼저 따로 커밋합니다. 쓴 페이지를
커밋한 뒤에 이슈를 닫고(확인할 일로 남긴 변경이 있으면 not planned, 아니면 completed), 사이트를 다시
올립니다. 메모는 사용자의 컴퓨터만 쓰고 저장소의 파일은 아무도 쓰지 않으므로, 두 변경이 병합에서
부딪치지 않습니다.

자기 사이트의 이슈만 가져오므로 두 메모가 받는 곳 하나를 함께 써도 됩니다. git이 없으면 기다립니다.
커밋해야 이슈를 닫을 수 있기 때문입니다. 기다려야 하는 배포(로그인, 보호 설정)는 남겨 두었다가 5분마다,
요청하면 바로 다시 올립니다.

변경은 그 줄에 페이지가 보여 준 할 일이 페이지가 보여 준 상태로 남아 있을 때만 반영합니다. 줄이
옮겨졌으면 같은 글이 그 페이지의 한 줄에만 있을 때 그 줄을 찾습니다. 그 밖에는 추측하지 않고, 오늘
저널에 줄과 고른 상태를 적은 WAITING 할 일을 남깁니다. 변경마다 id로 기록하므로(`.excudo/received.json`)
같은 묶음을 두 번 읽어도 두 번 바꾸지 않습니다. 다음 웹 사이트가 메모에 반영된 변경을 페이지에
알리면, 페이지는 그 변경을 더 기다리지 않습니다. Vercel Authentication이 페이지처럼 함수도 지키며,
함수는 웹 사이트 자신의 페이지에서 온 요청만 받습니다.

직접 만든 예약 실행에서는 `site pull` 아래 단계인 `excudo receive --input <파일|->`를 쓸 수 있습니다. 묶음
하나, 묶음 목록, `gh issue list --json number,body`의 출력을 받습니다. 미리 보기(`--dry-run --json`)는 쓸
페이지를 `writes`에, 결과마다 그 변경이 쓴 파일을 `file`에 알려 주며, 이미 받은 변경도 마찬가지입니다.

### 홈의 대시보드

`dashboard`는 웹 사이트 홈 맨 위, 사용자의 홈 위에 대시보드를 둡니다. 원하는 구성을 원하는 순서로
적습니다. 구성마다 접는 상자이며 `open: false`가 아니면 펼쳐져 있고, 제목 줄에 숫자가 보이며,
접고 편 상태는 기기가 기억합니다. 이 설정이 없으면 홈은 전과 같습니다.

```js
site: {
  dashboard: {
    sections: [
      { type: "links", title: "업무", items: [{ title: "Jira", url: "https://…", icon: "J" }] },
      { type: "notes", page: "메모장" }, // 그 노드의 본문을 보며 고치는 보드. 받는 곳이 있어야 함
      { type: "tasks", except: ["보관"] }, // 상태별 열린 할 일, 지난 목표일, 할 일이 많은 노드(nodes: 8).
                                     // except의 노드와 그 아래 노드의 할 일은 세지 않음
      { type: "done", weeks: 8 },      // 주마다 끝낸 할 일
      { type: "agents", days: 14 },    // 날짜별 에이전트 세션, 비용, 맡긴 일
      { type: "runs", days: 7 },       // 예약 실행 단계별 마지막 결과, 실패한 것 먼저
    ],
  },
},
```

`group`은 여러 구성을 접는 상자 하나에 담고, 상자 안에서 구성마다 제목을 붙여 보여 줍니다:
`{ type: "group", title: "링크", sections: [{ type: "links", title: "업무", items: […] }, …] }`. 안의
구성은 묶음과 함께 접히므로 `open`을 받지 않고, 메모장과 다른 묶음은 넣지 않습니다. 묶음의 제목 줄은
링크만 담은 묶음이면 링크 수를 더해 보여 주고, 그 밖에는 구성마다 첫 숫자를 보여 줍니다.

링크는 새 탭에서 열리고 페이지에 관한 정보를 보내지 않습니다. `icon`은 한두 글자이며, 없으면
제목의 첫 글자를 씁니다. 페이지가 다른 사이트의 그림을 불러오지 않기 때문입니다. 숫자는 웹
사이트를 쓸 때 계산하며, 대시보드가 기준 시각을 함께 보여 줍니다. 끝낸 할 일은 열린 줄을 `DONE`으로
바꾼 커밋의 주에 셉니다. 끝낸 할 일을 다른 페이지로 옮긴 것은 다시 세지 않으며, 커밋마다 센 결과는
`.excudo/dashboard-done.json`에 남습니다.

메모장은 보드입니다. `page`가 가리키는 노드의 본문(제목과 요약 아래, 생성된 하위 문서 위)을 그
자리에서 보고 고치며, 한 줄이 한 항목이고 Tab과 Shift+Tab으로 줄을 들이거나 냅니다. 저장하면 본문
전체를 할 일 상태와 같은 길로 받는 곳에 보내고, 고치기 시작한 본문의 다이제스트를 함께 보내므로
그 이슈에는 사용자가 쓴 글이 남습니다. 빈 줄은 빠지고 목록 항목이 아닌 줄은 항목이 됩니다. 메모가
받기 전까지는 모든 기기에 저장한 보드가 대기 표시와 함께 보입니다. 저장하지 않은 수정은 기기에
남고, 수정 취소는 저장한 보드로 되돌립니다.

`site pull`은 노드가 고치기 시작한 본문 그대로이면 저장한 본문으로 바꿉니다. 그사이 Tine이나 다른
기기에서 바뀌었으면 줄 단위로 합칩니다. 서로 다른 줄의 수정은 모두 남고, 같은 자리에 더한 줄도
모두 남습니다. 같은 줄을 서로 다르게 고쳤으면 노드 쪽을 두고, 웹에서 쓴 줄은 보드 맨 아래의
'겹친 수정' 항목 아래에 붙여 Tine이나 보드에서 직접 고르게 합니다. 고치기 시작한 본문을 노드의 최근
커밋과 앞선 저장에서 찾지 못하면, 줄을 더하기만 한 저장은 그대로 반영하고 그 밖의 저장은 무엇을 지웠는지
알 수 없으므로 통째로 그 항목 아래에 붙입니다.

## 작업자와 독립 검토자 정하기

개선 작업을 구현할 에이전트 하나와 결과를 읽기 전용으로 검토할 에이전트 목록을 정합니다.
엔진은 역할 설정과 실행 인자를 보여 줍니다.
에이전트 실행은 호출자가 맡습니다.
`agents set`, `agents accept`, `agents decline`은 사용자가 요청하거나 승인한 뒤에만 실행합니다.

```js
agents: {
  worker: { tool: "codex", model: "gpt-6.1-sol", effort: "high" },
  reviewers: [
    { tool: "codex", model: "gpt-6.1-sol", effort: "xhigh" },
    { tool: "claude", model: "claude-opus-5-5", effort: "xhigh" },
  ],
  suggest: true,
},
```

`excudo.config.mjs`의 `agents`는 선택 설정입니다.
설정이 없으면 역할을 미정으로 보고합니다.
`agents --json`은 값과 출처, 권장값, 응답 대기 중인 제안을 보여 줍니다.
모델과 추론 수준을 비우거나 생략하면 도구 기본값을 따릅니다.

Codex 기본값은 `~/.codex/config.toml` 최상위의 `model`, `model_reasoning_effort`에서 읽습니다.
Claude 기본값은 CLI에 맡깁니다.
네트워크와 API 키는 쓰지 않습니다.

Codex 모델은 `~/.codex/models_cache.json`에서 읽습니다.
`CODEX_HOME`이 정해져 있으면 그 폴더에서 읽습니다.
`visibility: "list"`인 항목을 `priority` 오름차순으로 정렬합니다.
캐시가 없으면 오류 없이 목록 없음으로 보고합니다.

Claude 목록은 `src/agents.mjs`의 `CLAUDE_MODELS`에 순서대로 있습니다.
현재 Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5 순서입니다.
ID는 `claude-fable-5-2`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`입니다.
추론 수준은 `low`, `medium`, `high`, `xhigh`, `max`입니다.
목록을 갱신할 때 이 상수와 시험, 영문, 국문 README를 함께 고칩니다.

최상위 모델은 제공사 목록의 첫 항목으로 추정합니다.
이 등급은 성능 측정 결과가 아닙니다.
권장은 두 번째 모델을 쓰며 작업자는 `high`, 검토자는 `xhigh`를 씁니다.
검토자 권장에는 작업자와 다른 제공사의 모델을 포함합니다.

두 번째 모델이나 지원하는 추론 수준이 없으면 해당 권장값은 미정으로 둡니다.
사용자가 직접 고른 최상위 모델은 유지합니다.
경고 없이 '최상위, 사용자 선택'으로 표시합니다.

```sh
npx --no-install excudo agents
npx --no-install excudo agents set worker --tool codex --model gpt-6.1-sol --effort high
npx --no-install excudo agents set reviewer --index 0 --tool claude --model claude-opus-5-5 --effort xhigh
npx --no-install excudo agents args worker --for orca
npx --no-install excudo agents args reviewer --index 0 --for cli
npx --no-install excudo agents suggest --new --json
npx --no-install excudo agents accept <id>
npx --no-install excudo agents decline <id>
```

화면의 검토자 번호는 1부터, `--index` 인자는 0부터 시작합니다.
`set`은 다음 인덱스에 검토자를 추가할 수 있습니다.
도구 기본값을 쓰려면 `--model "" --effort ""`를 넘깁니다.

`args --for orca`는 `orca orchestration worker-start`에 붙일 인자를 출력합니다.
`args --for cli`는 선택한 CLI에 붙일 인자를 도구 이름 없이 출력합니다.
빈 값의 플래그는 생략합니다.
응답 대기 중인 제안은 stderr에 승인 명령과 함께 알리며 종료 코드는 0입니다.

처음 관찰한 목록을 기준으로 새 상위 모델을 제안합니다.
Codex의 `upgrade` 필드와 목록에서 사라진 설정 모델도 제안 조건입니다.
직접 고른 모델이 최상위였던 역할에만 최상위로 바꾸자는 제안을 냅니다.
호출자는 새 모델을 쓸지 사용자에게 먼저 묻습니다.

`agents suggest --new`는 알리지 않은 제안만 출력하고 알린 것으로 표시합니다.
알린 때, 승인, 거절, 첫 모델 목록 지문은 `.excudo/agents.json`에 남습니다.
거절한 제안은 다시 내지 않으며 `suggest: false`는 제안을 끕니다.

설정 편집은 기본 내보내기 객체 맨 앞의 표식 구역을 씁니다.
파일에는 줄 시작의 `export default {`가 하나만 있어야 합니다.
다른 설정의 import, 함수, 정규식, 템플릿 문자열과 스프레드는 바이트 단위로 유지합니다.
기존 `agents` 값이 리터럴이면 처음 고칠 때 표식 구역으로 옮깁니다.
리터럴이 아니거나 내보내기가 모호하면 수동 편집을 안내합니다.

```js
export default {
  // excudo:agents start
  agents: { worker: { tool: "claude", model: "claude-opus-5-5", effort: "high" } },
  // excudo:agents end
  // 다른 설정은 이 자리에 둡니다.
}
```

이후 편집은 표식을 포함한 구역만 바꿉니다.
매번 별도 Node 프로세스에서 실제 설정을 import하고 `agents` 값을 확인합니다.
import가 실패하거나 값이 다르면 원문을 복원하고 필요한 수동 편집 값을 안내합니다.
사용자가 동시에 편집한 내용은 보존합니다.

## 명령

작업 폴더에서 `npx --no-install excudo <명령>`으로 실행합니다. 위치는 `--root`,
현재 폴더와 그 위의 `excudo.config.mjs`, `EXCUDO_ROOT` 순서로 정합니다. 작업 폴더를
찾지 못해도 `start`, `feedback`, `update`(`--apply` 제외)는 실행됩니다. 그 밖에는 `init`과 `skills --global`을 뺀 모든 명령이 멈추고 그 사실을 알립니다.

| 명령 | 동작 |
| --- | --- |
| `start [--json]` | 지금 어디까지 했는지 보여 줍니다. 이 컴퓨터에서 마친 처음 단계와 다음 단계를 명령과 함께 알려 주며, 작업 폴더가 없어도 실행됩니다 |
| `start --report [--json]` | 처음 단계마다 마쳤는지와 이어서 할 곳을 파일을 바꾸지 않고 알려 줍니다 |
| `update [--channel latest\|next] [--apply] [--json]` | 레지스트리를 확인하고 변경 이력과 명령을 보여 줍니다. 설치한 버전이 프리릴리스면 `next`를 따릅니다. `--apply`는 작업 폴더에서 업데이트를 설치하고 스킬을 갱신합니다 |
| `feedback [--title <글>] [--message <글>] [--details] [--out <파일>] [--json]` | 정리한 제보 초안과 링크를 이 컴퓨터에서 만듭니다. 아무것도 보내지 않으며 작업 폴더 없이도 실행됩니다 |
| `init [폴더]` | 설정, 지침, 스킬과 그래프를 만듭니다. 기존 파일은 보존합니다 |
| `build [--force]` | 뷰와 하위 트리를 생성합니다. force는 손으로 고친 생성물을 덮어씁니다 |
| `check [--json]` | 노드와 참조를 검사합니다. JSON에 `top`이 있고 오류는 종료 코드 1입니다 |
| `instructions [--json] [--limit <바이트>] [--check]` | AGENTS.md 크기와 후보를 읽고 한도 초과를 검증합니다 |
| `instructions move --lines <시작>-<끝> --to <스킬> --reference <이름> --pointer <문구> [--since <커밋>]` | 기존 작업 폴더 스킬로 원문을 옮깁니다 |
| `tree [노드]` / `tree --path <노드>` | 하위 트리 또는 맨 위까지의 경로와 요약을 출력합니다 |
| `home [--own] [--json]` | 홈을 누가 쓰는지, 사용자 홈이 임베드한 것과 빠진 것을 봅니다. `--own`은 홈을 넘겨받고 트리를 아카이브로 옮깁니다 |

| `fix [--dry-run] [--json]` | id를 함께 쓰는 블록을 고칩니다. 같은 복사본은 첫 블록의 임베드로, 다른 블록은 새 id로 바꿉니다 |

| `mirror mark [이름] --wrote <출처>=<파일> [--note <출처>=<파일>]` | 작업 폴더가 메모에 쓴 줄을 그 메모의 기준으로 기록합니다 |
| `mirror text [이름] [출처] [--copy] [--json]` | 메모가 가질 글을 출력하거나, 메모의 표식 사이에 붙여 넣도록 클립보드에 넣습니다(`--copy`) |
| `snapshot [--only <파일>] [--settle N] [--json]` | 정리 전에 그래프의 사용자 편집, 남김 기록, 설정을 먼저 커밋합니다. `--only`(여러 번, 작업 폴더나 그래프 기준 경로 또는 그래프 안의 절대 경로)를 주면 그 그래프 파일만 따로 커밋합니다. 없는 경로는 아무것도 커밋하지 않고 종료 코드 1을 냅니다. 또 `--settle N`을 주면 `idle --settle N`이 `settled`로 보는 편집만 커밋합니다 |
| `save <메시지>` | 검사, 생성, 상태 줄 출력 후 그래프, `review.json`, `sources.json`, `reflect.json`, `skills.json`, 학습한 스킬, `excudo.config.mjs`를 커밋합니다. 그래프 잠금을 쥐고 실행하며 `private-line`, `sync-conflict` 경고도 알립니다. 없는 `--only` 경로는 아무것도 커밋하지 않고 종료 코드 1을 냅니다. `--only <파일>`(여러 번, 작업 폴더나 그래프 기준 경로 또는 그래프 안의 절대 경로)을 주면 그 파일과 생성이 쓴 파일만 커밋하고, 생성 전에 이미 다른 사람이 바꿔 둔 파일은 뺍니다. 그래서 예약 실행은 그사이 메모의 다른 곳에 쓴 편집을 그 사람의 커밋으로 남겨 둡니다. `--generated`는 같은 방식으로 생성이 쓴 파일만 커밋합니다 |
| `idle [--minutes N] [--settle N] [--json]` | 예약 실행이 지금 메모를 바꿔도 되는지 알려 줍니다. 쓰는 곳이 없으면 종료 코드 0, 다른 명령이 그래프 잠금을 쥐고 있거나 커밋하지 않은 그래프 파일(생성 페이지와 `EXCUDO_HOLD`에 보류한 파일은 빼고)이 최근 몇 분 안에 바뀌었으면 1, 일시 정지 줄이 있으면 3입니다. `--settle N`은 N분 동안 그대로이고 검사를 통과한 편집을 고치는 중이 아니라 끝난 편집(`settled`)으로 보고, 그보다 오래됐는데 검사를 통과하지 못한 편집은 `unsettled`로 냅니다 |

| `queue [--json]` | 에이전트에게 맡긴 열린 할 일을 처리 대기와 검토 대기로 나눠, 노드, 작업 폴더, 방침과 함께 보여 줍니다 |
| `queue report <키> --summary <말> [--file <보고서>] [--stamp <지문>]` | 에이전트의 보고를 할 일 아래에 대기 줄로 남깁니다. 개인 정보로 보이는 요약을 거부하고, 맡을 때의 지문을 주면 같은 문구의 할 일이 있는 파일에서 그사이 바뀐 할 일도 거부합니다 |
| `runs [--days N] [--step <이름>] [--failed] [--deferred] [--full] [--json]` / `runs add <단계> --status <상태>` | 예약 실행의 단계를 보거나 기록합니다. `--step`은 여러 번 쓸 수 있고, 상태 옵션 둘을 함께 쓰면 어느 쪽이든 고릅니다. 글 출력의 이유는 160자까지이며 `--full`로 전체를 봅니다. JSON은 이유를 그대로 냅니다 |

| `skills lint [이름\|폴더]... [--json]` | 스킬이 스킬 규칙을 지키는지 검사하고 점수를 매깁니다. 작업 폴더 밖에서는 엔진의 스킬을 검사합니다 |

`review`는 첫 목록 경고와 비활성 노드(사용자 홈이면 홈 밖의 맨 위 노드), 뒤처진 요약, 빈 노드와 긴 본문과 오래된 노드,
기한이 지났거나 오래된 할 일, 확인 표지, 오래된 생각, 중복, 오래된 저널, 폴더가 없어진 경로 줄을 찾습니다. 나이는
파일 수정 시각이 아니라 git log와 blame으로 셉니다. 이력이 없거나 짧으면 나이 후보는
생략하고 상대적인 요약 갱신은 계속 확인합니다. 이력을 끝까지 읽지 못하면 `review`와
`check`는 나이를 추측하지 않고 그 사실을 알립니다. 접힘, 생성 영역의 변경과 노드 이동은
본문 변경으로 세지 않으며 본문 삭제는 변경으로 봅니다. 완료와 기록, 그리고 그 아래의
노드는 빈 노드, 오래된 노드, 뒤처진 요약으로 묻지 않습니다. `1/5`처럼 연도가 없는 날짜는
가장 가까운 날짜로 해석합니다. 별도 줄의 `DEADLINE:`과 `SCHEDULED:`는 해당
할 일에 속하고 같은 문구의 할 일도 ID를 개별로 받습니다. 남김은 `keepDays`가 지나거나
내용이 바뀌면 만료됩니다. `top`의 뒤처진 요약 수에는 남김으로 기록한 요약을 세지 않습니다. JSON의 `questions`, `mergedReasons`, `suppressedQuestions`는
질문 수, 묶어서 줄인 사유 수, 남김으로 숨긴 질문 수입니다. `--limit`는 질문 묶음 수이며
한 명령 안에서 문서 수집과 git 분석을 공유하고, 커밋된 내용의 요약값과 blame 결과는
`.excudo/history.json`에 캐시합니다. 후보만 내며 스스로 옮기거나 지우지 않습니다.
기존 남김 ID도 대상 하나를 가리키면 유지합니다. 같은 문구의 할 일이 공유하던 ID는 어느
항목을 남겼는지 알 수 없으므로 각 항목을 따로 다시 물어봅니다.

| 검사 | 수준 |
| --- | --- |
| `node-title`, `node-summary`, `duplicate-name`, `orphan-folder`, `list-trailing-text` | 오류입니다 |
| `block-id-duplicate`, `block-ref-missing`, `embed-cycle`, `reflect-invalid` | 오류입니다 |
| `summary-long`, `top-summary-long`, `list-wide`, `node-large`, `doing-wide` | 경고입니다 |
| `dangling-link`, `bullet-heading`, `heading-spacing`, `paragraph-gap`, `skills-outdated`, `history-failed` | 경고입니다 |
| `embed-page-missing`, `embed-twice`, `path-duplicate`, `path-window-twice`, `knowledge-missing` | 경고입니다 |
| `sync-conflict`, `private-line` | 경고입니다 |
| `instructions-size` | 경고입니다 |
| `instructions-target` | 알림입니다 |

`sync-conflict`는 동기화 앱이 충돌 뒤에 남긴 사본(`*.sync-conflict-*`, `(conflicted copy)`)을
알리며, 트리는 이 사본을 읽지 않습니다. `private-line`은 마지막 커밋 뒤에 들어간 줄 가운데 note
출처가 버리는 규칙에 걸리는 줄을 파일과 줄 번호로만 알리며, 커밋한 줄은 다시 알리지 않습니다.
`list-wide`는 홈의 메타 노드와 날짜별 보관 노드를 제외합니다. 기본값은 요약 120자,
첫 목록 요약 60자, 목록 9개, 한 노드의 열린 할 일 12개, 진행 중인 할 일 9개입니다(`doingMax`는 `widthMax`를 따르고,
`taskMax: false`나 `doingMax: false`를 주면 그 할 일 수를 세지 않습니다). 외부 출처의 노드는 받은편지함이므로
이보다 많아도 됩니다.

## 세션 지침 크기 관리

`excudo instructions`는 `AGENTS.md`에서 작업 폴더 스킬로 옮길 절차를 보고합니다.
보고 명령은 한도를 넘어도 파일을 읽기만 합니다.
기본 한도는 줄바꿈을 포함한 32,768바이트이며 목표 크기는 한도의 85%입니다.
`instructions: { limit: 65536, target: 49152, auto: false, keep: ["항상", "프로젝트 > 안전"] }`으로 값을 정합니다.
`target`은 한도보다 작은 0 이상의 정수이며 `null`이면 기본값을 씁니다.

`excudo check`는 한도를 넘으면 `instructions-size` 경고를 냅니다.
목표를 넘고 한도 이내면 `instructions-target` 알림을 냅니다.
둘 다 예약 저장을 막지 않습니다.
작업 폴더의 검증에서 `instructions --check`를 실행하면 한도 초과 시 1, 나머지는 0으로 끝납니다.
목표를 넘으면 한 줄로 알리고 목표 이하면 아무것도 출력하지 않습니다.

```sh
npx --no-install excudo instructions --json
npx --no-install excudo instructions --check
npx --no-install excudo instructions --limit 65536
```

`instructions: false`나 `{ limit: false }`면 크기 제한과 후보 보고를 끕니다.
`--limit <바이트>`는 꺼진 제한도 이번 보고에 한해 바꿉니다.
설정한 목표가 새 한도보다 작으면 유지하고, 나머지는 새 한도의 85퍼센트를 목표로 씁니다.
파일이 없으면 크기는 0이고 후보도 없습니다.

`instructions.keep`에는 제목이나 ` > `로 이은 전체 제목 경로를 넣어 절과 하위 절을 고정합니다.
`<!-- excudo: keep -->`를 제목이나 최상위 목록 항목 바로 앞줄에 두어 원문을 고정합니다.
고정 항목은 중첩된 줄을 포함하며, 같은 절의 다른 항목은 후보로 남습니다.
엔진 템플릿 규칙은 언제나 원문대로 남습니다.

보고의 `pinned`는 고정한 절, 항목과 템플릿 규칙의 바이트 수이며 겹친 부분은 한 번만 셉니다.
`movable`은 나머지 크기이며 후보가 아닌 글도 포함할 수 있습니다.
`pinnedBlocks`는 보호 블록의 이름, 줄 범위와 크기를 담습니다.
`pinned`가 `target` 이상이면 `targetBlocked`가 참이고 큰 보호 블록을 경고로 알립니다.
크기 경고와 검증 명령도 이 이유를 알리며 검증의 종료 코드는 한도로만 정합니다.

후보는 512바이트 이상인 `##` 또는 `###` 절이나 최상위 목록 항목입니다.
코드 펜스와 주석 안의 제목과 항목은 블록으로 보지 않습니다.
작업 폴더 스킬을 명시하거나 명령, 코드 펜스, 번호 단계, 중첩 항목 세 개 이상의 절차 근거가 있어야 합니다.
후보는 큰 순서로 나열하고 겹치지 않으며, 옮길 수 있는 절 전체가 개별 항목보다 우선합니다.

가장 많이 언급한 작업 폴더 스킬을 대상으로 제안합니다.
백틱 안의 이름과 스킬 경로를 세며, 동률이면 이름순으로 고릅니다.
`skills.dir`과 `.agents/skills/`에서 찾고 엔진 스킬은 제외합니다.

명시한 작업 폴더 스킬이 없으면 기존 이름과 겹치지 않게 제목으로 새 이름을 제안합니다.
제목에 영문자와 숫자가 없으면 `workspace-procedure-<줄>`을 씁니다.
엔진 스킬을 언급했다는 이유만으로 일반 규칙을 작업 폴더 절차로 보지 않습니다.

제목 절 하나나 최상위 목록 항목 하나를 원문 그대로 옮깁니다.

```sh
npx --no-install excudo instructions move --lines 40-72 --to release-notes --reference release --pointer "배포 근거를 보존할 것." --dry-run
npx --no-install excudo instructions move --lines 40-72 --to release-notes --reference release --pointer "배포 근거를 보존할 것."
```

대상은 이미 있는 작업 폴더 스킬이어야 하며 엔진 스킬은 거부합니다.
고정한 글, 엔진 템플릿 규칙, 일부만 지정한 블록도 거부합니다.
`--since`가 없으면 `AGENTS.md`, 대상 `SKILL.md`, 기존 참고 파일이 추적 중이며 변경이 없어야 합니다.
원문은 `skills/<스킬>/references/<이름>.md`에 붙이고 새 파일에는 제목을 만듭니다.
`SKILL.md`의 참고 절을 재사용해 링크를 한 번만 추가합니다.

기존 블록은 두 개까지 지정한 `--pointer` 줄로 바꾸며, 필요하면 대상 스킬을 알리는 문구를 붙입니다.
이 파일들과 지침 캐시만 쓰며, `--dry-run`은 쓰지 않고 `--json`은 결과를 출력합니다.
명령 자체는 스킬을 만들지 않습니다.

`--since <기준>`을 지정하면 저장한 기준 커밋 이후 여러 블록을 한 번에 옮길 수 있습니다.
템플릿 규칙, 고정한 글, 삭제 구간을 보존할 때만 지침과 스킬의 미커밋 변경을 허용합니다.
다음 블록을 옮기기 전에 보고를 다시 읽어 현재 줄 범위를 찾습니다.

삭제 구간은 기준 문서의 2/3단계 제목 절과 최상위 목록 항목 경계에서 나눕니다.
각 조각의 줄은 한 파일 안에서 붙어 있어야 하며 기준 커밋만큼 자주 나와야 합니다.
서로 다른 참고 파일로 옮겨도 각 조각이 보존되면 통과합니다.
양쪽에서 `AGENTS.md`와 스킬의 Markdown을 합쳐 검사하고, 빈 줄뿐인 조각은 무시합니다.
기준은 git에서 읽고 HEAD와 비교하며, `--uncommitted`를 지정하면 작업 트리와 비교합니다.

커밋 전에는 스킬 검사에 `--trim-since <기준> --uncommitted`를 지정합니다.
지침, 스킬, 기록과 링크의 변경만 허용하며 다른 미저장 작업은 계속 검사합니다.
`--uncommitted`가 없으면 이동 결과도 저장한 상태여야 합니다.

`excudo-skills`는 요청받으면 절차를 옮기고 매 세션 필요한 규칙은 안내 줄에 남깁니다.
`instructions.auto: true`면 예약 실행에서 한도를 넘을 때 정리를 시작하고 목표 크기까지 옮깁니다.
이동 명령으로 큰 후보부터 옮기며 대상 스킬의 설명이 절차를 포함하는지 확인합니다.
새 작업 폴더 스킬은 이미 있는 스크립트, 검사, 알려진 성공/실패 사례로 만들 수 있어야 합니다.
그렇지 않으면 블록을 남기고 이유를 보고합니다.

보존 검사, `excudo check`, `skills lint`를 통과한 뒤 지침과 스킬을 함께 한 번 커밋합니다.
검사가 실패하면 바꾼 파일을 기준 커밋에서 복원하고 이번 실행에서 만든 파일만 삭제합니다.
`auto`를 켜지 않으면 예약 실행은 후보만 보고합니다.
보호된 크기 때문에 목표에 도달할 수 없어도 한도를 넘으면 자동 이동을 계속합니다.
한도 이내가 되면 보호 블록을 보고하고 정리를 멈춥니다.

JSON은 파일을 `file`, `exists`, `bytes`로 나타냅니다.
예산은 `enabled`, `limit`, `target`, `auto`로 나타냅니다.
초과 여부는 `aboveTarget`과 `over`이며 후보의 최소 크기는 `threshold`입니다.
`candidates`는 `kind`와 `headingPath`, 양끝을 포함한 `startLine`/`endLine`으로 블록을 나타냅니다.

각 후보에는 `bytes`와 `target`, `engineSkills`와 `reason`도 있습니다.
후보 원문은 출력하지 않습니다.

`lastTrim`은 마지막 정리의 크기와 커밋이고 `growth`는 이후 바이트 증가량입니다.
기록이 없으면 둘 다 `null`입니다.
이동이 성공하면 무시되는 `.excudo/instructions.json` 캐시에 기록합니다.

보존 검사를 통과하고 `AGENTS.md`와 스킬 파일을 커밋하면 정리 커밋으로 갱신합니다.
다른 메모의 미저장 변경으로 전체 검사가 실패해도 갱신하며 검사의 실패 종료 코드는 유지합니다.
`--uncommitted`, `--facts`, `--self-test`는 캐시를 갱신하지 않습니다.
텍스트 보고도 기록이 있으면 증가량을 출력합니다.

## 설정

```js
export default {
  graph: "notes",
  locale: "ko",       // en 또는 ko입니다.
  private: [],       // 제보 진단에서 지울 문자열입니다.
  summaryMax: 120,
  topSummaryMax: 60,
  widthMax: 9,
  taskMax: 12,       // false면 한 노드의 열린 할 일 수를 세지 않음
  doingMax: undefined, // 진행 중인 할 일의 최대 수. widthMax를 따르고, false면 세지 않음
  doneKeep: 5,
  metaNodes: ["완료", "기록"], // 기본값은 해당 언어의 라벨입니다.
  staleDays: 30,
  keepDays: 90,
  bodyMax: 20,
  sources: [],        // 외부 출처입니다. "외부 작업 가져오기", "지식을 최신으로 유지하기", "다른 앱의 메모 따라가기"를 참고합니다.
  knowledge: [],      // 참고 지식만 담는 노드입니다.
  interests: undefined, // 회고 스킬이 오래 갈 결정을 두는 노드입니다.
  conversations: false, // 코딩 에이전트에 입력한 요청을 읽습니다. true 또는 { claude, codex, exclude }입니다.
  moved: {},          // 이름을 바꾼 폴더의 이전 경로와 새 경로입니다. 경로 줄과 요청에 씁니다.
  skills: {},         // 학습 스킬입니다. { dir, install, keep, minScore, minRequests, minSessions, windowDays, dormantDays, similarity }
  instructions: { limit: 32768, target: null, auto: false, keep: [] }, // 목표 기본값은 한도의 85%이며 auto는 예약 정리를 켭니다.
  exports: [],        // 메모로 쓰는 사용자 형식의 파일입니다. "사용자의 형식으로 파일 유지하기" 참고
  agents: undefined, // 작업자와 독립 검토자 설정(선택)
  queue: {},          // 에이전트에게 맡긴 할 일입니다: { tag, limit }. "에이전트에게 일 맡기기" 참고
  site: undefined,    // 메모로 쓰는 웹 사이트입니다: { out, title, mode, open, journals, css, onSave, inbox, publish }. "메모를 웹 사이트로 보기" 참고(inbox: true 또는 { github: { repo }, schedule })
  labels: {},         // 생성하는 단어를 바꿉니다.
}
```

`excudo.config.mjs`는 그래프 밖에 둡니다. 메타 노드를 order로 지정하지 않으면 맨 끝에 둡니다.
`messages`, `review`, `recommendations` 같은 라벨 묶음은 항목 단위로 합칩니다.
줄 머리말과 확인 표지(`markers`: `생각:`, `방침:`, `#확인`)는 언어 설정과 관계없이 모든 언어의 것을
알아봅니다.
기본 홈 쿼리는 DOING만 펼칩니다. 언어나 생성 절의 라벨을 바꿀 때는 기존 생성물의 경계를
확인한 뒤 강제 빌드합니다.

## Tine과 휴대폰 동기화

그래프 폴더(기본 `notes/`)를 Tine에서 엽니다. macOS에서 다른 그래프로 바꾸려면 앱을 완전히
끈 뒤 실행합니다.

```sh
TINE_GRAPH=<그래프폴더> /Applications/Tine.app/Contents/MacOS/tine <그래프폴더>
/Applications/Tine.app/Contents/MacOS/tine doctor <그래프폴더>
```

켜진 앱에 `open -a`나 `tine open`으로 경로를 넘겨도 그래프가 바뀌지 않습니다.
0.6.986의 `tine export`는 “Rebuilding the query index…”에서 실패했습니다. 0.7.1에서는 내보내기가
되지만, 그래프 검증에는 내보내기 대신 `tine doctor`를 씁니다.
Tine이 없으면 [tine.page](https://tine.page)에서 설치합니다.

Syncthing으로 그래프만 공유하고 파일 변경 감지와 휴지통 방식의 30일 보관을 켭니다.
Android의 Syncthing-Fork로 연결한 뒤 동기화 폴더를 Tine에서 엽니다. `.stignore`는 뷰,
아웃라이너 백업과 엔진의 임시 파일을 PC에 남깁니다. 급히 적은 것은 저널에 두고 정리 인터뷰로 노드에 옮깁니다.
엔진, 스킬, 캐시, 남김 기록은 휴대폰에 공유하지 않습니다.

## 개발

CLI 시간 제한 검사를 재현할 수 있도록 테스트 파일을 순서대로 실행합니다.

```sh
npm install
npm run example
npm test
npm pack --dry-run
npm run release:check
```

빌드 단계 없는 ESM JavaScript와 node:test를 씁니다. 두 README와 두 언어를 함께 고칩니다. 두 언어의
메시지가 같은지는 테스트가 확인합니다. CI는 Linux, macOS, Windows에서 Node 22와 24로 테스트하고 묶은 tarball을 설치해 봅니다.
필요한 환경이 없으면 macOS 앱과 POSIX 전용 대역 검사를 건너뜁니다.

git 이력을 읽는 라이브러리 함수(`check`, `review`, `keepCandidates`, `move`, `archive`)는 Promise를
돌려주며, blame은 여러 파일에 동시에 실행합니다.
엔진은 레지스트리 패키지 `@cudoment/cudoc@^1.1.0`을 씁니다.

깊이 6, 생성물 보호와 접힘 유지, NFD 이름, 명령, 날짜를 고정한 git 후보, 완료 보관, 설치,
환경 변수, 커밋된 예시를 검사합니다. 코드 예시 보존, 캐시 삭제, 이동 후 보호, 묶음 남김,
CLI 인터뷰의 답변 반영, 저장, 해당 묶음 되돌리기, 읽지 못한 이력, 이력 캐시, 이동 후 나이,
보관 보호도 검증합니다. Tine doctor와 모델 호출 없는 Codex 스킬 인식은 설치되어
있으면 검사하고 없으면 전제 조건과 함께 건너뜁니다. 수동 Claude Code, Codex 인터뷰 검증은
`test/fixtures/messy/`의 사본을 쓰며 개인 메모는 쓰지 않습니다.

엔진 버전을 올릴 때 입구 스킬의 버전 범위도 바꿉니다. 테스트가 정합성을 확인합니다.
게시하기 전에 `npm run release:check`를 실행합니다(`npm publish`도 먼저 실행합니다). 복제본이 `main`에
커밋되어 있는지, 버전에 아직 태그가 없는지, 입구 스킬이 그 버전을 설치하는지, 테스트가 통과하는지,
예시가 최신인지, 모든 스킬이 100점인지, 패키지에 들어갈 파일이 맞는지 확인합니다. 로컬 복제본을
`file:`로 쓰는 작업 폴더는 계속 복제본을 실행합니다. 게시한 버전으로 옮기려면 그 폴더에서
`npm install excudo@^<버전>`을 실행하고 검사를 돌립니다. 연결한 스킬은 `node_modules`를 거쳐
가리키므로 어느 쪽이든 따라갑니다.
`src/dialects/logseq.mjs`에 아웃라이너 문법을 모으며, `skills/`가 스킬의 유일한 원본이고 두
에이전트 폴더에는 링크만 둡니다. 개인 메모는 복제본 밖이나 무시되는 `private/`에 둡니다.
패키지에는 스킬, 템플릿, 더미 예시가 들어가고 캐시는 빠집니다.
